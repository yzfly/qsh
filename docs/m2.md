# M2: self-optimizing connections

Status: design approved for implementation; target releases 0.3.0 – 0.5.0 (section 13.4).

This document is the design and the implementation plan of milestone M2 (DESIGN.md sections 7
and 8): connections that measure their path and adapt, on every Linux distribution, without
anybody tuning a knob. It is precise enough to implement and to test against. Wire formats and
other interoperability rules are normative in [protocol.md](protocol.md) (sections cited as
"protocol §7.8"); the security consequences are in [security.md](security.md). Where this
document and protocol.md disagree, protocol.md wins and this document is a bug.

## 1. Goals, non-goals and how we know we are done

**Goal.** On a lossy, long path (the TokenSSH reference path: a phone in China to a server
abroad, RTT ≈ 270 ms, loss ≈ 6 %), on a network that blocks UDP, behind a NAT that forgets idle
mappings after 15 s, and on a freshly installed server of any supported distribution, `qsh host`
is as good as the path allows, with no configuration, and tells the user in one line what to fix
when the host could do better.

**Success criteria** (each is a test in section 12 or a check in section 8):

| # | Criterion | Measured by |
|---|---|---|
| S1 | Reconnecting on a network where UDP is blocked starts the working transport at once: attached within 1 RTT + handshake of the transport, not after the 3 s pipe stagger or an 8 s QUIC timeout | chaos `udp-blocked-memory` |
| S2 | Output written by the program while the client is idle behind a NAT with a 15 s UDP timeout reaches the client within 1 s, after at most one learning step | chaos `nat-rebinding` |
| S3 | Ctrl-C typed during an output flood shows its effect within **2 RTT + 100 ms + snapshot / throughput** (p50), and within 3 RTT + 300 ms + snapshot / throughput (p95), at loss up to 10 % | chaos `flood-interrupt` |
| S4 | Recovery after an address change ≤ 3 s, after UDP is blocked mid-session ≤ 12 s, with no byte of pipe-session output lost and every tty byte either delivered or covered by an announced gap | chaos `address-change`, `udp-block-midway` |
| S5 | Compressible output (build logs) on a 2 Mbit/s path arrives ≥ 2.5 × faster than without compression | chaos `compression` |
| S6 | `qsh-server doctor` names every host-side problem of section 8 with the exact fix for the distribution it runs on, on the nine distributions of the CI matrix; `tune --apply` followed by `tune --revert` leaves the host byte-for-byte as before | distros workflow |
| S7 | Replacing `qsh-server` with a newer version and running `qsh host` again keeps every session, its output and its exit status | chaos `upgrade` |
| S8 | qsh beats ssh and matches or beats mosh on every row of the published benchmark (section 12.4) except predictive echo, which is M3 | bench workflow |

**Non-goals for M2**: predictive echo (M3), a root daemon listening on 443 for all users (M4),
changing the protocol version (everything here is a compatible qsh/1 extension, protocol §13.2),
multipath, forward error correction, any network access at runtime other than the protocol
itself (doctor does not call cloud metadata services).

## 2. Path measurements, shared by everything below

Every mechanism in this milestone consumes a few estimates. They are computed in one place on
each side so that decisions agree with each other and with what `~s` and `qsh doctor` show.

| Estimate | Side | Source | Used by |
|---|---|---|---|
| `srtt`, `min_rtt` | both | QUIC: `quinn::Connection::rtt()` (= `stats().path.rtt`, smoothed); the minimum is our own decaying minimum of it (section 6.3; quinn exposes none). Mux transports: PING/PONG (the client already pings every 15 s; the server PINGs at each attach and every 5 s while the connection has an attachment) | `min_rtt`: pacing and catch-up (6.3); `srtt`: race stagger, doctor, `~s` |
| loss | client | QUIC: `lost_packets / sent_packets` of `PathStats`, over the connection and over the last 30 s | path memory, doctor, `~s` |
| `T`, delivery rate of output | server, per attachment | acknowledged output offsets per second (section 6.3) | pacing, catch-up, compression |
| path MTU | client | QUIC: `PathStats::current_mtu` (quinn runs PLPMTUD, RFC 8899) | doctor |
| observed address | client | PATH_INFO (protocol §5.6) | NAT detection, keepalive learning |

`T` is measured in **output offsets** (uncompressed bytes), so compression raises `T` and every
formula that converts bytes into time stays right when compression is on.

## 3. Path memory

### 3.1 What it is for

Every reconnect today runs the same race (protocol §12.1): QUIC at once, TLS after 400 ms, the
ssh pipe after 3 s. On a network that drops UDP, every reconnect pays a QUIC handshake timeout
before TLS wins; on a network where only ssh gets through, it pays 3 s. A laptop returns to the
same few networks every day. Path memory remembers, per destination and per network, what worked
and what did not, and starts with the winner.

### 3.2 Keys

An entry is keyed by **(destination, network)**:

- **Destination key** `d` = the first 16 bytes of `HMAC-SHA256(salt, "qsh-path-dest\0" ||
  host)`, where `host` is the name or address the client dials for QUIC and TLS
  (`Target::host`, lowercased). Ports are not part of the key; they are facts stored inside
  the entry, because the same host serves the same networks whatever its port.
- **Network key** `n` = the first 16 bytes of `HMAC-SHA256(salt, "qsh-path-net\0" ||
  NetKey)`. `NetKey` is a coarser view of the network than the change detector's
  `NetFingerprint` (netwatch.rs), so that a new DHCP lease on the same Wi-Fi is still the same
  network. For each address family with a default route, in the order IPv4, IPv6, it is the
  family tag (4 or 6), the interface name, the gateway address (or a zero byte when there is
  none), and the route's source address masked to /24 (IPv4) or /64 (IPv6), each field
  length-prefixed exactly as `NetSnapshot::fingerprint` encodes them. The interface addresses
  list is not part of it. `NetKey` is computed by a new `NetSnapshot::path_key()` in netwatch.rs.
- **salt**: 32 random bytes created with the file. A file copied to another machine reveals,
  for a given guess of a host name, whether it is in the file (as with ssh's `HashKnownHosts`);
  the salt only prevents precomputed tables.

A cellular connection without a gateway and with a carrier-NAT address yields the same key for
every carrier on the same modem interface. That is accepted: a wrong guess costs one race, and
the record corrects itself (section 3.5).

### 3.3 What an entry holds

```json
{"d":"9f…(32 hex)","n":"41…(32 hex)","day":20366,
 "t":{"quic":{"port":60443,"ok":20366,"hs":420},
      "tls":{"port":443,"ok":20360,"hs":610,
             "fail":{"kind":"timeout","n":2,"retry":1791193600}},
      "ssh":{"ok":20101,"hs":1900}},
 "last":"quic","rtt":270,"loss":0.06,"ka":10}
```

| Field | Meaning |
|---|---|
| `day` | last use, in whole days since the Unix epoch (UTC) |
| `t.<transport>.port` | the port that last worked for this transport (QUIC, TLS); absent for ssh |
| `t.<transport>.ok` | day of the last success |
| `t.<transport>.hs` | handshake time in ms (QUIC/TLS: to the end of the TLS handshake; ssh: to the pipe preface), exponentially weighted (α = 0.3) |
| `t.<transport>.fail` | present while the transport is considered blocked here: `kind` (`timeout`, `reset`, `hello`), `n` consecutive failures, `retry` (Unix seconds) when to probe again |
| `last` | the transport that won the last race here, or that the sessions last moved to: the tie-break between transports that worked the same day, without storing a time |
| `rtt` | smoothed RTT in ms of the last connection (EWMA α = 0.3) |
| `loss` | QUIC loss ratio of the last connection (EWMA α = 0.3), 0 – 1 |
| `ka` | learned NAT keepalive interval in seconds (section 4), absent: the default |

**Failure kinds.** Only failures that say something about the *network* are recorded:

| Kind | Observed as | Recorded? |
|---|---|---|
| `timeout` | no answer to the handshake within the attempt timeout (UDP or TCP silently dropped) | yes |
| `reset` | TCP reset or unexpected end of stream during the TLS handshake (middlebox) | yes |
| `hello` | handshake completed, no SERVER_HELLO within 5 s (deep packet inspection); over QUIC only if at most 2 of the server's packets arrived after the handshake: more say the path is slow (20 % loss over 600 ms), not blocked, and count as `error` | yes |
| refused | ICMP port unreachable / ECONNREFUSED: nothing listens on that port | no: a fact about the daemon, which the next bootstrap reply corrects |
| pin mismatch | protocol §9.4 | no: handled by re-bootstrapping, never a path fact |
| not tried | the race ended before the attempt started | no |

A QUIC or TLS attempt that started no later than the winning attempt and has not answered when
the race is decided is recorded as `timeout` at once (a client may be killed right after a
reconnect, before the attempt's own timeout); an answer that comes later clears it.

**No poisoning.** A failure is recorded as `fail` only when, in the same race or within 60 s,
another transport reached the same destination on the same network. When the whole network is
down every attempt times out; that must not mark every transport blocked. On a lossy path (the
entry's measured `loss` 15 % or more) a single `timeout` is chance rather than a block: the
transport stays in the race until it times out a second time in a row (WP-1 notes).

### 3.4 Storage, bounds, privacy

- One file, `$XDG_STATE_HOME/qsh/paths.json` (default `~/.local/state/qsh/paths.json`), mode
  0600 in the 0700 state directory, created and replaced like the session state files
  (security.md §4.4): temporary file with mode 0600, fsync, rename, fsync the directory.
  Concurrent `qsh` processes read-modify-write it under an exclusive `flock` on
  `paths.json.lock`; a process writes at most once per 10 s and when it exits, except that a
  change of the blocked transports, of `last` or of `ka` is written at once (a client may be
  killed right after a reconnect).
- Format: `{"qsh_paths":1,"salt":"<64 hex>","entries":[…]}`. An unknown `qsh_paths` version, a
  file over 1 MiB, invalid JSON or an invalid entry: the file (or the entry) is ignored and
  replaced on the next write, with one debug log line. Path memory can never stop a connection.
- Bounds: at most 256 entries; when full, the entry with the oldest `day` is dropped. An entry
  unused for 30 days is dropped. A `fail` whose `retry` has passed and that was then probed
  successfully is removed; `retry` is never more than 24 h ahead.
- Privacy: hashed destinations and networks only; no addresses, no interface names, no list of
  times. Days instead of timestamps for everything except an active `retry` deadline, which
  disappears once the transport works again. One entry per (destination, network): the file
  records which networks were used for a host, not when or how often.
- `path_memory = false` (section 11) disables reading and writing it. Deleting the file is the
  documented way to forget; `qsh doctor` shows the entry of the current network.
- Embedders (the hub) use the same file through `Paths`; an embedder can pass its own path or
  disable it.

### 3.5 How the race uses it

The race (protocol §12.1, transport/mod.rs `Race::start`) takes a **plan**: a list of
`(transport, port, delay)` attempts. Without an entry, or when the entry is older than 30 days,
the plan is the default (QUIC primary port at 0, TLS at 400 ms, ssh at 3 s, extra ports as in
section 5.3). With an entry:

1. **Start the winner at once.** The winner is the transport not marked `fail` with the most
   recent `ok` (ties: `last`, then QUIC, then TLS, then ssh); among attempts at 0 ms it is
   listed first. Its remembered port, if it is still among the ports of the
   bootstrap reply, is tried first, at 0 ms. If the winner is ssh, the pipe starts at 0 ms.
2. **Skip what is known to fail here.** A transport with a `fail` whose `retry` is in the future
   is not part of the race. It is probed in the background (section 3.6).
3. **Adapt the stagger.** When QUIC is in the race and has an `hs`, TLS starts after
   `clamp(1.5 × hs_quic, 250 ms, 2 s)` instead of 400 ms: on a 270 ms path a QUIC handshake
   takes 2 RTT ≈ 540 ms, and a 400 ms stagger starts TLS for nothing on every reconnect.
4. **Never get stuck.** If a race with skipped transports fails entirely, the next attempt
   (immediately, without back-off) runs the full default plan, and the entry's `fail` marks are
   cleared: the memory was wrong. A memory miss is always the default race. Path memory changes
   the order and timing of attempts, never the set of transports allowed by `transports`.
5. **Record the outcome** of every attempt that finished (success or a recorded failure kind)
   into the entry for the network the race ran on. If the network changed during the race, the
   outcome is not recorded.

### 3.6 Background re-probe and transport upgrade

While a session is connected on network `n`, for each skipped transport whose `retry` has passed,
the client makes one background attempt: transport handshake and the hello exchange, then GOAWAY
(NO_ERROR) and close; no ATTACH, so it never interferes with the session (protocol §7.2 allows
one outstanding ATTACH per session). Back-off of `retry` after each failed probe: 1 min, 5 min,
30 min, 2 h, 12 h, then 24 h. A success removes `fail`.

**Transport upgrade.** When a background probe succeeds with a transport better than the current
one (QUIC > TLS > ssh pipe: only QUIC survives address changes, and the pipe has head-of-line
blocking through ssh), the client SHOULD move its sessions to it: it keeps the probe connection,
and once no input is unacknowledged and no ATTACH is outstanding it re-attaches every session of
the old connection on the new one (an ordinary resume, protocol §7.3), then closes the old
connection with GOAWAY (NO_ERROR). It ignores the SESSION_TAKEN_OVER that arrives on the old
streams (protocol §11.2 permits this to the client that moved its own session). The upgrade must
attach within the server's `AUTH_TIMEOUT` (10 s after the hello) or the probe connection is
dropped. At most one upgrade per server per 60 s.

**A late answer is an upgrade too.** An attempt that was still running when the race was
decided and succeeds later (section 3.3), or whose hello was still under way (the hellos of a
race run concurrently, and one without an answer after 5 s is kept until 10 s; WP-1 notes), is
treated like a successful probe when its transport is better than the winner's: on a lossy path a lost QUIC Initial costs QUIC its first PTO
(about 1 s), and TLS, started 400 ms or `1.5 × hs` later, can win the race although QUIC
works. The client keeps the late connection, makes the hello exchange on it, and moves the
sessions to it under the conditions above (the old connection carries a session; no upgrade in
the last 60 s); it then becomes `last`, so the next race on this network starts with it again.
Otherwise its success is recorded and it is closed.

### 3.7 Code

- `qsh-core/src/client/paths.rs` (new): `PathMemory` (load, lookup, record, flush), the file
  format, the keyed hashing. Pure logic plus file I/O; unit tests with a temporary state dir.
- `transport/mod.rs`: `RaceConfig` becomes a `Plan` (list of attempts); `Race::start` runs it;

- `client` pool: build the plan from `PathMemory` + config, record outcomes, run background

### 3.8 Suspected paths: racing before a path is declared dead

The dead path rules (protocol §12.3: typed input unanswered for 8 s, nothing received for
45 s) date from the phone era and are deliberately conservative: declaring a live path dead
tears down a connection that would have answered. They made S4's "UDP blocked mid-session"
cost 1 s (the harness types after a second) + 8 s + a TLS race and attach at 270 ms (about
1.1 s) + process noise: 11.0 – 12.3 s against a limit of 12 s. The client now separates
*suspecting* a path from *declaring it dead*:

1. **Suspicion.** Typed input is unanswered and nothing at all has arrived on the connection
   (no message, and over QUIC no UDP datagram: the server's acknowledgements of a keep-alive
   or of a tail probe prove the path) for
   `T = max(2 s, 4 × SRTT + 4 × RTTVAR, floor)`.
   SRTT is QUIC's own estimate on QUIC; RTTVAR (and SRTT on TLS and the pipe) is smoothed
   RFC 6298-style from the connection's own exchanges: the hello, the transport handshake that
   made the connection (one round trip for QUIC, two for TCP and TLS 1.3; the pipe's is not a
   sample), then each PONG. Before a second sample RTTVAR is half the first, as in RFC 9002.
   The handshake sample matters: on the terrible profile netem's `reorder 10 %` sends some
   packets without delay, and a TLS connection whose only sample was such a 291 ms hello (the
   path's round trip is 600 ms) was suspected after 2 s of TCP retransmissions, and its
   session moved to QUIC (one run of 18, before the handshake was a sample). Four round trips cover a lost
   packet and its retransmission (QUIC declares a packet lost after 9/8 RTT and probes after
   one PTO ≈ SRTT + 4 RTTVAR); the variation term grows with a path whose delay jumps (a
   radio, queues), and PONGs queued behind a flood inflate it, which only makes the client more
   patient. `floor` starts at 2 s and is raised by false alarms (below).
2. **Background race.** The session tells the pool (`Conn::suspect`), once per connection; the
   pool's monitor of that connection runs a race in the background **without** giving the
   connection up, and PINGs it once more. The plan is the one path memory gives for a reconnect
   (its order, its left-out transports, its remembered ports), except that every direct
   transport starts at once, including a new connection of the suspected one's transport (its
   path may be fine and the connection not: a TCP connection in exponential back-off after a
   blip, or lost server state); the ssh pipe keeps its planned start.
3. **Whichever answers first carries the sessions.** The race is checked every 50 ms and once
   more after its winner's hello: if anything arrived on the old connection since the
   suspicion, the race is dropped with its attempts, **nothing is recorded** in path memory, and
   `floor` of that connection becomes `min(1.5 × the silence it showed, 6 s)`, so a path that is
   merely slow (a phone's radio waking up, a burst of losses) does not start a race on every
   keystroke. Otherwise the winner becomes the slot's connection and the old one is abandoned
   (`Conn::abandon`): its sessions leave it at once, with their input unacknowledged (unlike a
   transport upgrade, 3.6, which waits for it), and attach on the winner; the old connection
   gets GOAWAY and is closed once they left. Any transport may take over (the path is what
   failed, not the transport), and the upgrade interval of 3.6 does not apply.
4. **Hard limits stay.** A race that finds nothing leaves the connection to the dead path rules
   (8 s, 45 s, the QUIC idle timeout), and the connection is not suspected again. When those
   fire while a race still runs, the race is dropped and the sessions reconnect as before.

**Exactly once, one ATTACH.** The background race never attaches: only sessions do, after
leaving the old connection, so protocol §7.2's one outstanding ATTACH per session holds as it
does for every reconnect. A session that was waiting for ATTACHED on the abandoned connection
abandons that ATTACH (its stream reset with CANCELLED) before it attaches on the winner. Input
is committed to the session by offset (protocol §7.3, §7.4): the new ATTACHED reports the
server's `received`, and the client resends from there, so input the old path delivered is not
repeated and input it lost is not lost; the server stops reading the old stream before it takes
that value. Nothing the session sent on the old connection after the new ATTACH exists: its pump
is gone.

**Path memory.** The race records like any race (3.3 – 3.5): its winner as `won`, a direct
attempt that started with it and was unanswered when it won as a timeout (QUIC on a network that
just started dropping UDP, which is what S1's next process needs), failures only when another
transport reached the server (no poisoning). A race dropped because the old path answered
records nothing.

**Why not lower the 8 s instead.** On the terrible profile (600 ms, 20 % loss each way) an
exchange can take 2 – 3 s (section 6.4); a lower hard limit would tear down live QUIC
connections there and put the sessions on TLS, whose congestion control collapses at that loss
(Ctrl-C 4.6 – 16.8 s, WP-1 notes). A suspicion costs at most a few handshake packets, and the
old path keeps the sessions unless it is really silent for `T` plus a handshake and a hello of
another transport: with tail probes every quarter round trip behind unanswered input on QUIC
(6.4), all of them and their acknowledgements lost at 20 % each way is about 0.36¹² ≈ 5 × 10⁻⁶.

**Radio cost.** Suspicion needs typed input, so an idle session never races; a false alarm
costs a TCP SYN and a QUIC Initial (and their handshakes, if they complete before the old path
answers, then GOAWAY) and raises the connection's threshold.

**Measured** (local rig, debug build, `udp-block-midway`, crossborder 270 ms, 6 % loss): echo
after the block 4.4 s in 5 of 6 runs (1 s before typing, 2 s suspicion, TLS 0.84 s, attach
0.27 s, echo 0.27 s), 5.8 s with a lost SYN; before: 11.0 – 12.3 s.

Code: `client/conn.rs` (`Mark`, `heard_since`, `suspect_after`, `suspect`, `rescue_over`,
`abandon`, the RTT estimate), `client/session.rs` (the pump's timer, and leaving at once when
abandoned, also while waiting for ATTACHED), `client/pool.rs` (`Monitor::rescue`,
`Pool::rescue`, `rescue_plan`, `Pool::take_over`; `Pool::race` takes an abort condition).
Transcript events `suspect` and `rescue` (WP-1 notes). Tests: `client/pool/tests.rs`, sessions
over fake transports on paused time: a silent path replaced by TLS at the threshold plus its
handshake, the input exactly once and one ATTACH per connection; a slow path that answers at
2.5 s keeping its session, nothing recorded, the threshold raised to 3.75 s and no race at the
next 3 s silence; a race that finds nothing, after which the 8 s rule reconnects.

## 4. NAT keepalive learning

### 4.1 Why it matters

A NAT forgets a UDP mapping after some idle time: RFC 4787 asks for at least 2 minutes, but
carrier NATs commonly use 30 s and some home routers 10 – 20 s. QUIC survives a lost mapping
(the next client packet creates a new one, the server sees an address change and validates the
new path, protocol §9.1), but **until the client sends something, everything the server sends
goes to the dead mapping and is lost**. For a user that is the worst kind of failure: the long
build finished, its output is on the server, and the terminal shows nothing until the next
keystroke or keepalive. The keepalive interval must stay below the NAT's timeout, and on a phone
every keepalive wakes the cellular radio for several seconds, so it must not be lower than
needed either.

### 4.2 Detection

The server sends PATH_INFO whenever the observed address of a connection changes (protocol
§5.6; the daemon checks every 500 ms). The client concludes that **a NAT timed out** when all of
these hold:

1. a PATH_INFO on a QUIC connection reports an address or port different from the previous
   PATH_INFO of that connection;
2. the client did not cause it: no `QuicClient::rebind` and no network change (NetWatch) in the
   last 10 s, and the local address of the endpoint is unchanged;
3. the connection had been idle in the client-to-server direction: in the `K` seconds before the
   PATH_INFO arrived the client sent nothing but keepalives (no INPUT, no ACK, no RESIZE). A
   rebinding while traffic flows is a NAT doing something else (pool pressure, a changed public
   address), not a timeout, and is not used for learning;
4. no other learning step for this network in the last 60 s.

### 4.3 Algorithm

Per network entry (section 3), `K` is the keepalive interval:

| Event | New `K` |
|---|---|
| no entry, or no `ka` | `K = 20 s` (`KEEPALIVE_START`) |
| NAT timeout detected (4.2) | `K = max(K / 2, 5 s)` (`KEEPALIVE_MIN`), saved at once |
| 30 min of attached, idle-capable time on this network at the current `K` without a detected timeout | `K = min(K × 1.25, 25 s)` (`KEEPALIVE_MAX`), saved |
| network changes | `K` of the new network's entry |

Growth is slow and bounded, so an oscillation costs at most one delayed output per 30 minutes
per network, and the floor of 5 s keeps the radio cost bounded on pathological NATs. The ceiling
is 25 s because the QUIC idle timeout is 60 s (protocol §9.1): two lost keepalives must not end
the connection.

`keepalive = <seconds>` in the configuration (qsh_config(5), 1 s – 1 h) disables learning and
uses that value; `keepalive = "auto"` (the default) is this algorithm. With an explicit value
above 25 s the client also raises its `max_idle_timeout` to three times the value (QUIC uses the
smaller of both peers' values, so this only lets the client keep a connection open longer when
the server allows it; the server advertises 60 s, section 4.4).

### 4.4 Mapping to quinn and to PING

- **QUIC keep-alive.** `TransportConfig::keep_alive_interval` is fixed when quinn creates a
  connection, and quinn has no API to change it later. The client therefore builds its
  `ClientConfig` per connection (it already does, for the pin) with `keep_alive_interval = K` of
  the network the connection starts on. When `K` of the current network later drops below the
  connection's value (a learning step, or a migration to another network), the client sends an
  application PING every `K` while the connection is idle, until it is replaced; when `K` grows
  the connection keeps its smaller value (harmless).
- **No application PING on idle QUIC connections.** Today the client sends PING every 15 s on
  every transport. On QUIC that is a second, redundant wake-up (PING plus PONG) and it would hold
  the NAT open regardless of `K`, making learning meaningless. In M2, on QUIC: the QUIC
  keep-alive keeps the mapping and elicits the server's ACKs; liveness is "no UDP datagram
  received for `max(45 s, 3 K)`" (quinn `ConnectionStats::udp_rx.datagrams` does not advance),
  and RTT comes from quinn. On TLS and the ssh pipe nothing changes: PING every 15 s (TCP
  mappings live much longer, and the mux layer has no keep-alive of its own).
- **Server.** The daemon keeps `keep_alive_interval = 20 s` on its side (it only matters when the
  client is gone or silent; the client's keep-alive is the one that holds a client-side NAT) and
  `max_idle_timeout = 60 s`.

### 4.5 Mobile radio cost

On LTE and 5G a packet promotes the radio to its high-power state for a "tail" of roughly 5 – 10 s.
With `K = 20 s` the radio is up a third to a half of the time while a session is attached; at
`K = 5 s` it never sleeps. The design keeps the cost down by: never going below what the network
needs (learning, floor 5 s); one wake-up per interval instead of two (no application PING on
QUIC); no keep-alive at all when no session is attached (the server closes connections without
attachments after 60 s, protocol §12.5, and the client does not keep them); and growing back
after 30 quiet minutes. Embedders that know the device is on battery or on a metered network
(TokenSSH) may pass a higher `keepalive_max` through the library API.

## 5. Extra ports and port fallback

### 5.1 What is realistic in M2

Networks that block UDP or "unusual" TCP ports usually still allow 443 (HTTPS and HTTP/3). The
daemon is a per-user process and cannot bind ports below 1024 unless the administrator allows
unprivileged users to (`net.ipv4.ip_unprivileged_port_start`, Linux 4.11+, per network
namespace, applying to IPv4 and IPv6). Giving the daemon `CAP_NET_BIND_SERVICE` would mean file
capabilities on a binary every user runs; that is rejected. A system service that owns 443 for
every user and hands connections to per-user daemons needs its own authentication and is M4
(`qshd`, DESIGN §8).

So M2 provides:

- `extra_ports` in `[server]` (qsh_config(5)): more ports the daemon tries to bind, on UDP and
  on TCP independently, in addition to the first free port of `ports`. Typical values: a second
  unprivileged port that a firewall allows (`[61443]`), and 443 on a single-user host where the
  administrator lowered `ip_unprivileged_port_start` (documented by doctor, section 8, with its
  trade-off; `tune` changes it only with an explicit flag).
- Each extra port is bound "where it can": a port already in use (another user's daemon got it
  first, or a web server holds TCP 443) or not permitted (`EACCES`) is skipped with one log line
  and not announced. No `SO_REUSEPORT`: two daemons sharing a port would split one user's
  packets between them.
- At most 8 extra ports are used; more are a configuration warning.
- On an upgrade (section 10) the sockets are inherited, so the ports never become free for
  someone else to take.

### 5.2 Announcement

The bootstrap reply gets a new member, `extra_ports` (protocol §10.4):

```json
"extra_ports":[{"port":443,"udp":true,"tcp":false},{"port":61443,"udp":true,"tcp":true}]
```

Old clients ignore the member (unknown members are ignored, protocol §10.3) and keep using `udp`
and `tcp`; old servers do not send it. The client stores the extra ports with the session
credentials (state file, security.md §4.4), so that `qsh attach` and reconnects without ssh use
them too. Every port of a daemon presents the same certificate; pinning is unchanged.

### 5.3 Order of attempts

For each transport the client has a list of candidate ports: the remembered port of the path
memory entry if it is among the announced ones, then the primary port, then the extra ports in
announced order, without duplicates. Within one transport, the first candidate starts at that
transport's start time and each further candidate 300 ms after the previous one, while the
earlier ones keep running (a blocked UDP port shows as a timeout, so waiting for it would cost
the full attempt timeout). Example, default plan, `extra_ports` 443 (UDP, TCP):

| Time | Attempt |
|---|---|
| 0 ms | QUIC 60443 |
| 300 ms | QUIC 443 |
| 400 ms | TLS 60443 |
| 700 ms | TLS 443 |
| 3 s | ssh pipe (only if nothing has connected) |

At most 6 direct attempts run at once, below the server's limit of 8 unauthenticated connections
per source address (protocol §6.6). The first connection whose hello succeeds wins (protocol
§12.1); its transport *and port* go into path memory, so the next reconnect on this network
starts with QUIC 443 at 0 ms.

When the primary UDP port is blocked, QUIC on the first extra port still starts before TLS on
the primary port (300 ms against 400 ms) and needs one round trip less (QUIC handshake and
hello: 2 RTT; TCP, TLS and hello: 3 RTT), so it wins on a loss-free path: at 270 ms its hello
completes after about 840 ms, TLS's after about 1210 ms. With a remembered QUIC winner, TLS
starts `1.5 × hs` after it (section 3.5), about 2.3 RTT behind, and QUIC is done at 2 RTT. In
both cases a lost QUIC packet in the handshake costs QUIC about a second and lets TLS win; the
QUIC attempt goes on, and its late success takes the sessions over (section 3.6), so that QUIC
on the extra port remains the remembered winner. The order is deliberately not changed to start
QUIC on every port at 0 ms: on a network that drops UDP that would only add attempts that time
out.

## 6. Smart catch-up (SNAPSHOT)

### 6.1 The problem

qsh transports the exact bytes so that scrollback is complete. Its weakness is a burst of output
over a slow path: the user has to wait for all of it, and an interrupt takes effect only after
the backlog drains (mosh, which synchronizes the screen instead, has no such problem and no
scrollback). Smart catch-up keeps both: exact bytes whenever the path can carry them, the current
screen instead of a backlog that it cannot carry in about two seconds, with the skipped part
announced as a gap. The wire format and the content profile are normative in protocol §7.8.

### 6.2 The screen model

For every tty session the daemon keeps a terminal emulator state ("model") fed with exactly the
bytes it appends to the output replay buffer, in the pty reader thread and under the same lock,
so that the model state at offset `E` is available whenever the buffer's end is `E`.

**Choice: the `vt100` crate** (0.16, MIT, by Jesse Luehrs), behind a small internal trait
(`screen::Model`) so that it can be replaced:

| Criterion | `vt100` | own minimal model |
|---|---|---|
| Maturity | 13 M downloads, used by terminal multiplexers and TUI test tools; complete enough for vim, less, htop, tmux, shells | years to reach the same coverage |
| State we need | grid with SGR attributes, wide and combining characters, cursor and its visibility, alternate screen, scroll region, scrollback, application cursor and keypad, bracketed paste, mouse protocol mode and encoding, title and icon name | all to write |
| Dependencies | `vte` (the alacritty parser, Apache-2.0 OR MIT), `unicode-width`, `itoa` — all already common | none |
| Distributions | Debian: `rust-vt100` in bookworm (0.15.1), trixie (0.15.2), forky/sid (0.16.2); `rust-vte` 0.15 in trixie; Fedora: `rust-vt100`, `rust-vte` in dist-git | n/a |
| MSRV | 1.70 (ours: 1.85) | n/a |
| Risk | one maintainer; a panic on hostile output | the same risk, in our own code |

The risk is handled by: a fuzz target that feeds arbitrary bytes and resizes to the model and to
our snapshot encoder (round trip, section 12.1) and runs in CI; size caps (below); the
`screen::Model` boundary, which keeps the option of replacing the crate; and **fault
isolation**: a fault in the screen model disables catch-up for that session only (protocol
§7.8.7). Release builds unwind on panic (not `panic = "abort"`), and every call into the model,
the snapshot encoder and the codec runs under `catch_unwind`; a panic there drops the session's
model, logs it once with the session id, and the session goes on as one without a model (gap
plus redraw). The daemon and the other sessions are never affected.

**`vt100` 0.16 is required, not 0.15** (Q2, resolved): 0.15 has neither the faint attribute nor
`Screen::set_size`. For packagers: Debian forky/sid have 0.16.2; Debian 13 (trixie) has 0.15.2,
so a trixie package needs `rust-vt100` 0.16 packaged (or vendored); its `vte` 0.15 dependency is
in trixie already. `vt100` does not keep blink, invisible or strikethrough, so the snapshots of
this implementation leave them out (protocol §7.8.4 allows it).

**Our own encoder.** The snapshot bytes are produced by our code from the model's read API
(cells, attributes, cursor, modes), not by `vt100`'s `contents_formatted()`, so that the content
profile is exactly what protocol §7.8 allows and never contains a sequence copied from the
program's output. State of the profile that `vt100` does not keep (focus reporting, mode 1004;
the cursor style, DECSCUSR; whether origin mode or a non-ASCII character set was used since the
last clear, protocol §7.8.4) is followed by a small scanner of our own beside the model, in the
style of `AltScreen` in qsh-cli's screen.rs.

**Caps.** The model exists only while `cols ≤ 1024`, `rows ≤ 512` and `cols × rows ≤ 262 144`
(`MODEL_MAX_CELLS`); on a larger terminal the session has no model and behaves as in 0.2.0 (gap
plus redraw). It keeps at most `SNAPSHOT_TAIL_LINES` = 100 lines of its own scrollback (for the
tail, 6.5). Memory per session: about 40 bytes per cell for two grids plus the tail; for a
200 × 50 terminal ≈ 1.2 MB, against the 8 MiB replay buffer every session already has.
`snapshot = false` in `[server]` turns models and snapshots off.

**Cost.** Feeding the model is the only per-byte cost added to the daemon. Budget: ≥ 100 MB/s of
typical output (`seq`, compiler logs, `cat` of a source tree) per core on the CI runner; the
benchmark is part of the work package's acceptance.

**Hostile output.** The output may come from anywhere (`cat` of a downloaded file, a log, a web
page in a text browser), so what the model costs must not grow with what the output asks for.
`vt100` is never fed the program's bytes directly but the output of our scanner (`scan.rs`),
which has the same effect on the screen:

- **Strings** (OSC, DCS, SOS, PM, APC) never reach `vt100`: its parser (`vte` with its `std`
  feature) buffers an OSC without limit, so `printf '\e]0;'; yes` grew the daemon's memory with
  the output until the kernel killed it, and every session with it. `vt100` keeps nothing of a
  string that a snapshot uses (titles are the scanner's); a CAN takes the string's place.
- **Counts are clamped** to the screen's size before `vt100` loops on them: it repeats insert
  characters (`@`, quadratic), insert lines (`L`) and scroll down (`T`) as often as asked, so
  `CSI 65535 @` took 1.45 s per 8 bytes, with the model's lock held. Every repetition beyond the
  screen's width or height changes nothing, so the clamp is exact (a differential test against
  `vt100` checks it). Control sequences are held back until complete for this, and one longer
  than 64 bytes is passed on in a canonical form of what `vte` parsed.
- **A work budget.** What remains is work proportional to the screen (clearing it, switching
  screens, inserting lines and characters), which output can ask for in a loop. The scanner
  counts it per chunk, in cells; a model may spend 64 cells per byte of output plus 64 screens
  of the largest size per second, saved up to 32 such screens (a few per cent of a core at
  most). Output beyond that is not fed: the model is dropped as after a fault (protocol §7.8.7)
  and the session goes on without snapshots. Programs stay far below it (a full-screen program
  repainting, `clear` or `watch` in a loop, an editor scrolling a region).
- **Nothing waits for the model.** The reader thread feeds the model after appending the output
  to the replay buffer and releasing its lock (in order: it takes the sink's lock first), so the
  attachments, which read the buffer all the time, never wait for the model; they reach the
  model (resize, snapshot, the screen in use) on blocking threads, never on a tokio worker. The
  model may therefore be a chunk behind the buffer: a snapshot stands at the model's end, a
  resize is applied at the buffer's end at the time of the RESIZE (the model applies it when its
  output gets there), and a snapshot asked for before the model caught up with what was sent is
  taken when it has.

### 6.3 Throughput and pacing (server)

Per attachment and output stream the server keeps:

- **Delivery rate samples.** When an ACK advances `last_ack`, `delivered` = the offsets it
  newly acknowledges minus skipped ranges (OUTPUT_GAP, SNAPSHOT) inside them. A sample is the
  `delivered` of the ACKs since it began (with the ACK that ended the previous one) over the time
  since then, and it ends with the first ACK at least `max(1 ms, R / 4)` after its start: ACKs
  that arrive microseconds apart (coalesced by the path, the transport, or a client that was
  descheduled) are one sample, not a rate of gigabytes per second, which would pin the window at
  8 MiB, turn compression off and disable the backlog trigger for the 10 s of the filter. A
  sample is used only if the attachment was **not application-limited** during it (output was
  waiting in the replay buffer, `end > sent_end`, the whole time); otherwise it measures the
  program, not the path. A sample counts at most twice the current `T` (or the initial
  estimate): `T` doubles per sample at most, which follows a real increase within a few round
  trips but no burst.
- **`T`** = the maximum of the per-second averages of samples over the last 10 s (a windowed max
  filter as in BBR: robust against ACK delays; the minimum sample time and the growth cap above
  make it robust against bursts of ACKs). Before the first sample: on QUIC `cwnd / srtt` from
  quinn's `PathStats`; on the mux transports 1 MiB/s.
- **`R`** = the connection's **minimum recent RTT** (section 2), not `srtt`: a decaying minimum
  (a sample below it replaces it, and any sample replaces a minimum older than 30 s; 100 ms
  before the first sample). Samples: on QUIC, quinn's RTT estimate (`Connection::rtt()`), read
  each time a window is computed; on the mux transports, server PING → PONG, sent at each attach
  and every 5 s while the connection has an attachment. Why not `srtt`: a window above the
  path's capacity builds a queue in the transport (over the mux transports the PING waits in it
  too), the queue raises `srtt`, which raises the window, and `1.25 × T × (R + 100 ms)` grows
  without bound up to the 8 MiB cap, with an interrupt waiting behind all of it. The minimum is
  the path's delay without the queue the window causes (BBR's `min_rtt`).
- **Pacing window** `W = clamp(1.25 × T × (R + 100 ms), 64 KiB, 8 MiB)` for tty sessions;
  `2 × T × (R + 100 ms)`, at least 256 KiB, for pipe sessions (throughput matters more than
  interrupt latency there). This replaces the fixed 512 KiB (`PACING_WINDOW`, serve.rs). The
  1.25 gain lets the window grow when the transport could carry more; QUIC's BBR does the
  network-level probing.
- **Client ACK cadence while output streams.** A client that set ACCEPT_SNAPSHOT acknowledges
  every 16 KiB or 50 ms (instead of 32 KiB or 200 ms) while output arrives continuously
  (protocol §7.5 allows more frequent ACKs), but at most once per 10 ms: compressed frames carry
  64 KiB of output each, and a burst of them got an ACK per frame, each in a packet of its own
  (4 – 7 packets within 2 ms, measured), any of which, lost, holds up input typed after it on
  the same stream. This is what lets `W` stay within one RTT plus 100 ms of data and gives the
  Ctrl-C bound below.

### 6.4 When the server sends a snapshot

Only on a tty session, with `snapshot` negotiated, ACCEPT_SNAPSHOT set on the attachment, and a
model. Let `U = (end − last_ack) − Σ(skipped ∩ (last_ack, end])` (output neither acknowledged nor
skipped, protocol §7.6), `B = end − sent_end` (output not yet sent). At most one snapshot is in
flight (sent and not acknowledged), and one more for input: a backlog or resync trigger that
fires meanwhile waits for that snapshot's ACK, and then one fresh snapshot follows, rather than
a stack of screens queued behind each other; the input trigger does not wait (2):

1. **Backlog trigger.** `U > max(2 s × T, 256 KiB)` (`CATCHUP_AFTER` = 2 s,
   `CATCHUP_MIN` = 256 KiB) and `B > 0` (something to skip), evaluated whenever output is
   appended or an ACK arrives, once the attachment has at least 1 s of rate samples (or 500 ms
   on QUIC, which has a `cwnd` estimate).
2. **Input trigger.** The server accepts INPUT while `B > max(W, 64 KiB)`: the user wants to
   interact with the program now (Ctrl-C, `q` in a pager). The server stops sending from the
   backlog at once and takes the snapshot when the output pauses for 20 ms (counted from the
   input), or after 100 ms, whichever comes first, so that the snapshot usually already shows
   the program's reaction. The input trigger ignores the hysteresis (3), the sampling
   requirement (1) and a snapshot in flight: a Ctrl-C right after a backlog snapshot would
   otherwise wait for that snapshot's ACK, a round trip plus the queue ahead of it, and up to a
   second, against S3. (Measured before this rule, on the crossborder profile: the input arrived
   while a backlog snapshot was in flight in 4 of 5 runs, and waiting for its ACK cost 400 –
   450 ms of the 650 – 800 ms.) Only with two snapshots in flight does it hold the output until
   one is acknowledged. One input episode gives one snapshot; more INPUT while the server waits
   for the reaction does not restart the wait.
3. **Hysteresis** (backlog trigger only). No new backlog snapshot until the previous snapshot is
   acknowledged (an ACK with `Received ≥ Offset`) and 1 s has passed. Under a continuous flood
   on a slow path the steady state is therefore one screen per round trip plus a second: mosh's
   frame rate, adapted to the path. Resync snapshots (6.5, and after a mid-attachment gap) are
   not subject to it either.

When no snapshot can be made (over `MAX_SNAPSHOT`, or the model was dropped after a fault or
for its work budget, 6.2), the server sends OUTPUT_GAP to `E` and delivers SIGWINCH instead;
for the hysteresis that counts as a snapshot. With nothing to skip there is no gap: a resync
snapshot that cannot be made is replaced by SIGWINCH alone, and the backlog trigger waits for
more output before it tries again (the attempt, a capture and an encoding of up to two screens
at the caps, would only cost the same again). A snapshot whose text alone is over
`MAX_SNAPSHOT` is recognised before it is encoded. Output that fell out of the replay buffer is
skipped with OUTPUT_GAP right before the output after it, whatever is in flight (skipped bytes
are not in flight), and on an attachment with snapshots followed by a resync snapshot rather
than SIGWINCH (protocol §7.8.5); if the output that resync snapshot would follow fell out of the
buffer meanwhile too, the snapshot skips it instead. The gap is not sent each time the buffer's
base moves while the window is full: during a flood that overflows the buffer that was a gap
per chunk the program wrote, 2 000 – 12 000 OUTPUT_GAPs per three-second run in tiny packets,
which overflowed netem's packet queues on the lossy profiles (the server's QUIC declared 50 –
94 % of its packets lost, BBR's window fell to its minimum) and held the interrupt up for
5 – 29 s locally, 68 s on CI.

Sending it: the server takes the snapshot of the model at the end `E` of the output it has
processed (the buffer's end, or a chunk before it while the reader thread is feeding it; at or
after `sent_end`, else the server waits for the model), sends SNAPSHOT with `Offset = E`
(protocol §7.8; it replaces the output from `sent_end` to `E`), and continues streaming from
`E`. The snapshot's `Data` counts as in flight
for pacing until it is acknowledged. After a snapshot the server does not deliver SIGWINCH
(unlike after a plain OUTPUT_GAP): the screen is already right, and a shell does not repaint
anyway.

**Tail probes.** The snapshot that answers input is usually the last thing the server sends
for a while (the program was interrupted), so on QUIC a lost packet of it, or of the output
just before it, can only be found by QUIC's probe timeout: `srtt + 4 × rttvar + max_ack_delay`,
doubled for each further timeout without an acknowledgement, and quinn's probes carry new
data or the oldest unacknowledged packet's, not necessarily the lost one. Measured on the
crossborder profile, a snapshot packet lost twice in a row reached the client after 1.1 s. So
while that snapshot is not acknowledged, the server sends a PING on the control stream every
`max(R / 4, 20 ms)`, at most 12: the packets behind the snapshot make QUIC detect a lost one
by its time threshold, 9/8 of a round trip after it was sent, and acknowledgements keep the
probe timeout from backing off. They cost two small packets (PING and PONG) per quarter round
trip for a round trip or so, once per interrupt. The client does the same behind typed input
until it is acknowledged: from a quarter round trip after it while the server skips output (a
skip snapshot or a gap arrived in the last 5 s), else from 1.25 round trips, once the
acknowledgement is overdue (so ordinary typing on a working path sends none). The server holds
its output after an interrupt, the connection is idle in both directions, and a lost packet
of the Ctrl-C, or one before it on the same stream, waited for the client's probe timeout and
its backoff (3.8 s on the terrible profile, measured). (Over the mux transports TCP's own
retransmission applies.)

**Ctrl-C budget, without loss.** With `W` as in 6.3 in flight, a byte spends `W / T =
1.25 R + 125 ms` from being sent to its acknowledgement, `R` of it on the path and up to 50 ms
in the client's ACK delay: about `0.25 R + 75 – 125 ms` of output is queued (in the transport,
at the bottleneck or in the client) ahead of anything the server sends. An interrupt reaches
the server after R/2; the server stops sending the backlog, waits for the program's reaction
(20 ms of quiet, at most 100 ms) and sends the snapshot at once (also when another one is in
flight); the snapshot of size S waits behind the queue and arrives R/2 later: about
`1.25 R + 115 – 165 ms + S / T`, within the S3 target `2 R + 100 ms + S / T` for any R above
about 90 ms, and on short paths the settle is short too. A full 200 × 50 screen with colors is
10 – 40 KB (2 – 10 KB compressed, section 7); the 100 × 30 screen of the chaos test, 10 KB,
about 320 bytes compressed. Measured on the crossborder profile (270 ms, 6 % loss), runs
without a loss: 270 – 360 ms.

**Ctrl-C budget with loss.** The interrupt needs its input to reach the server and its
snapshot to reach the client, and on each of the two streams every packet sent before them
that is still unacknowledged (head of line: a terminal channel is one ordered stream): the
client's ACKs of the last round trip (at most one per 10 ms, 6.3; on the chaos flood 4 – 7
packets) and the server's last burst of output (compressed: 1 – 3 packets). Call their number
k; each is lost with probability p. A loss costs one recovery: QUIC detects it about 9/8 of a
smoothed round trip after the packet was sent, by the time threshold (the tail probes make
sure packets follow it), and the retransmission takes R/2 like the original, so about `9/8 R`
per loss (measured on the crossborder profile: 1.1 – 1.4 R); a retransmission can be lost
again. The number of losses L before the k packets are through is negative binomial,
`P(L = l) = C(k + l − 1, l) p^l (1 − p)^k`:

| p (per direction) | P(L = 0), k = 3 | P(L ≤ 1), k = 3 | P(L = 0), k = 8 | P(L ≤ 1), k = 8 | P(L ≤ 2), k = 8 |
|---|---|---|---|---|---|
| 6 % (crossborder) | 0.83 | 0.98 | 0.61 | 0.90 | 0.98 |
| 10 % (lossy) | 0.73 | 0.95 | 0.43 | 0.77 | 0.93 |
| 20 % (terrible) | 0.51 | 0.82 | 0.17 | 0.44 | 0.68 |

Measured with this implementation (debug build, chaos profiles): on crossborder about 40 % of
the runs had one recovery, which matches k ≈ 8. So at 6 % loss the p50 is the run without a
recovery (≈ 1.25 R + 140 ms, well within S3's p50 bound), but only just (P(L = 0) ≈ 0.6): a
p50 over five runs exceeds the bound whenever three of the five lose a packet, about one test
in four. S3's p95 allowance over the p50 bound, `R + 200 ms`, covers one recovery (`9/8 R` plus
timer slack). At 10 % with k = 8 even the p50 would need a recovery; on the lossy profile it
did not (more than half the runs had none), so fewer packets were exposed there.

**S3 beyond 10 % loss (approved 2026-10-06; p50 revised the same day).** S3 is specified for
loss up to 10 %; the terrible profile has 20 % each way. There, with k = 4 exposed packets (the
input, the snapshot, and one packet before each on its stream: the flood barely flows at
2 Mbit/s once compressed, so fewer packets are in flight than on crossborder), P(L = 0) =
0.41: the median itself usually pays a recovery, and the p95 three (P(L ≤ 2) = 0.90,
P(L ≤ 3) = 0.97). The p95 is therefore at least `1.25 R + 140 ms + 3 × 9/8 R ≈ 4.6 R + 140 ms`
(2.9 s at 600 ms), which no reliable in-order transport can beat: the terrible profile's p95
bound of 2.17 s, and its p50 bound of 1.37 s, are physically out of reach. For profiles
beyond S3's scope, with r_q(p) the smallest r with `P(L ≤ r) ≥ q` for k = 4:

- p50 ≤ `2 R + 100 ms + S / T + r50(p) × (9/8 R + 25 ms)`; r50 = 0 up to 15.9 % loss, 1 up to
  31 %;
- p95 ≤ `2 R + 100 ms + S / T + r95(p) × (9/8 R + 25 ms) + 200 ms`; r95 = 2 up to 15 %, 3 up to
  23 %.

For the terrible profile: p50 ≤ 2.07 s, p95 ≤ 3.67 s (the p95 bound approved before, with
k = 3, is the same: r95 = 3 at 20 % for both). Measured there (41 QUIC runs of the local rig
and of CI, binned by latency in steps of one recovery, 9/8 R + 25 ms = 700 ms, from about
1.2 s): 32 % without a recovery, 37 % with one, 24 % with two, 7 % with more, against 41 %,
33 %, 16 % and 10 % for k = 4; p50 1.33 s, p95 2.70 s, none over 3.67 s. Within S3's scope the
same mechanism explains the slow runs of the lossy profile (10 %): the runs of about 1 – 1.4 s
paid two recoveries on the critical path, for instance a lost snapshot whose loss QUIC could
only learn from the acknowledgement of a tail probe behind it, and that acknowledgement's
packet was lost too (packet captures: snapshot sent at 212 ms and lost, declared lost at about
800 ms, delivered at 963 ms); four of 18 runs, against P(L ≥ 2) = 0.15 – 0.23 for k = 6 – 8.

**Checking a quantile on nine runs.** A p95 over nine runs is their maximum, and a median of
nine over a bound that holds fails often: at 6 % loss about 40 % of the runs pay a recovery,
which alone takes a crossborder run over the p50 bound, and five or more of nine do so with
probability 0.27. The chaos check
therefore tests each bound as a statement about a fraction
of runs, with a one-sided binomial test: with `over` of `n` runs above a bound that should
hold at quantile q, it fails only if `P(X ≥ over) < 0.05` for `X ~ Binomial(n, 1 − q)`. A
system whose true quantile lies exactly on the bound fails such a check with probability at
most 5 % (less the more it beats the bound); with nine runs that allows 2 over the p95 bound
(3 would have probability 0.008, 2 have 0.071) and 7 over the p50 bound (8: 0.020). The
price is power: nine runs can only catch a gross regression of the median (eight or nine of
them over the bound), so the p50 and p95 values are recorded too, and a release run takes
more runs (`QSH_CHAOS_RUNS`; with 20, at most 3 over the p95 bound and 14 over the p50 bound).

### 6.5 Attach and FRESH: decision

**Decision: keep the 0.2.0 behaviour (a FRESH attach replays the scrollback), but bounded to
what the path carries in the catch-up budget, followed by a resync snapshot.**

At an attach that starts at `S` (`Output Received`, protocol §7.3), with snapshots usable: let
`budget = max(2 s × T₀, 256 KiB)`, `T₀` the initial estimate of 6.3.

- If `end − S ≤ budget` and `S ≥ base`: as today, stream from `S`.
- Otherwise (the backlog is too big, or `S < base` so there is a gap anyway): the server cuts at
  `C = max(base, end − budget)`, moved forward to just after the first `\n` within the next
  4 KiB if there is one (a cut inside an escape sequence garbles one sequence; a cut at a line
  start usually none). If the model's alternate screen is active at `end`, `C = end` (replaying
  part of a full-screen program's drawing into the normal screen would litter the scrollback).
  It sends OUTPUT_GAP `{S, C}` if `C > S`, streams `C .. end`, and then a **resync snapshot**
  (a SNAPSHOT whose `Offset` equals the expected offset: it skips nothing and repaints the
  screen and restores the modes that the cut may have lost).

So `qsh attach` on a fast path still shows the full scrollback; on a slow path it shows the last
two seconds' worth of it and the exact current screen, within about two seconds. Without the
`snapshot` capability (old peers, or `catchup = "off"`) the 0.2.0 behaviour is unchanged: replay
from `max(S, base)`, OUTPUT_GAP and SIGWINCH when there was a gap. An attach at LATEST gets a
resync snapshot instead of SIGWINCH.

### 6.6 What the snapshot reproduces

Normative in protocol §7.8.4. In short: both screens' contents with their attributes (SGR:
bold, faint, italic, underline, inverse, 16 / 256 / 24-bit colors; blink, invisible and
strikethrough are in the profile but `vt100` does not keep them, so this implementation leaves
them out), wide and combining characters, line wrapping, the cursor position and visibility,
which screen is active, the scroll region, the current SGR pen, application cursor keys and
keypad, bracketed paste, mouse tracking mode and encoding, focus reporting, the window title and
icon name, and for a skip while the normal screen is active up to 100 lines of the skipped
output's tail, pushed into the terminal's scrollback (a skip while the alternate screen is
active has no scroll-push and no tail). Not reproduced: older scrollback (that is the gap), the
saved cursor (DECSC), character set designations, origin mode, insert mode, tab stops, palette
changes, hyperlinks (OSC 8), images, the clipboard (OSC 52), bells, and anything that makes the
terminal answer (queries would inject answers as input into the session).

**The tail is approximate, by design** (protocol §7.8.4): the model counts line feeds on the
normal screen per output chunk, not scrolls. The tail is the lines that scrolled off since the
first chunk ending at or after the client's offset, minus `rows − 1` (the cursor may have been
anywhere on the screen, so the first line feeds may not have scrolled), at most 100: fewer lines
rather than lines the client already has. Scrolls without a line feed (a wrap at the bottom row)
are not counted. The client reports `Offset − S` as the skipped amount and never relies on the
tail.

### 6.7 The client side

- qsh sets ACCEPT_SNAPSHOT on tty sessions when its stdout is a terminal and `catchup` is not
  `"off"`; it never sets it for pipe sessions.
- On SNAPSHOT: it decompresses each part (protocol §7.12), assembles the parts (at most
  `MAX_SNAPSHOT`), checks the whole snapshot against the content profile (`check_profile`) and
  only then removes its own overlays (the status line of screen.rs), writes `Data` to the
  terminal, feeds the same bytes to its `AltScreen` tracker, sets `received = Offset` and
  acknowledges at once.
- Before a skip snapshot with a scroll-push (one that does not enter the alternate screen) it
  writes one dim line, `qsh: skipped 3.2 MB of output`, in order with the output (the session
  writes it, so embedders get it too). The snapshot's scrolling pushes it into the scrollback,
  where it marks the gap; the status line (`~s`) counts skipped bytes and snapshots.
- **A refused snapshot** (profile, assembly, size or a part's zstd frame) fails the channel
  (PROTOCOL_VIOLATION or FRAME_ERROR) without writing any of it, and the client then re-attaches
  that session **without ACCEPT_SNAPSHOT** for the rest of the process, logs a warning with the
  session, the offset and the reason, and counts it in `~s` (protocol §7.8.4, "After a refused
  snapshot"). A bug in a server's encoder then costs one reconnect, not a reconnect loop. After
  a rejected zstd frame (OUTPUT_ZSTD or a snapshot part, or a fault of our decoder) it also
  stops offering `zstd` on its later connections to that server for the rest of the process, at
  the latest after the second one.
- It ACKs as in 6.3.

### 6.8 Interactions

- **Upgrade (section 10):** the model's state travels in the handoff as a resync-snapshot byte
  string; the new daemon feeds it to a fresh model, which reproduces the profile exactly (that is
  what the round-trip test guarantees).
- **Compression:** snapshots are sent in parts of 32 KiB; a part is compressed when `zstd` is
  negotiated, `Data` ≥ 1 KiB and the frame is at least 10 % smaller.
- **Predictive echo (M3):** a snapshot is authoritative; it discards every pending prediction.

## 7. Compression (OUTPUT_ZSTD)

### 7.1 Format (normative in protocol §7.12)

Every OUTPUT_ZSTD carries one independent zstd frame (no shared context between messages, no
dictionaries), so replay, resume and gaps work unchanged: the replay buffer keeps uncompressed
bytes and the server compresses per send. The frame must be single-segment with its content size
declared, 1 – 65 536 bytes; the receiver checks the frame header before it decompresses anything.
That bounds a decompression bomb to 64 KiB of output per message and the decoder's window to
64 KiB, provided the decoder checks every copy against the declared size (7.3: `ruzstd`'s does
not). Snapshots can be compressed too (SNAPSHOT flag ZSTD, protocol §7.8).

### 7.2 When the server compresses

`zstd` negotiated (the client offers it unless `compression = "off"`; the server unless
`[server] compression = false`), and for the chunk at hand:

1. the **path's rate** is below `COMPRESS_BELOW` = 4 MiB/s (32 Mbit/s): above that the path is
   not the bottleneck and compression only costs CPU. The path's rate is not `T`: `T` counts
   output offsets (section 2), so compression raises it by the compression factor, and
   comparing `T` with the limit would switch compression off on a slow path as soon as it
   worked and back on 10 s later (when the rate window forgets). While compression is on the
   path's rate is `T × ρ`, with `ρ` the ratio of 3 (initially 0.5); while it is off (never
   started, or stopped by 3) it is `T`. Before the attachment's first rate sample (6.3) it is
   unknown, and the server compresses: the initial estimate (QUIC's `cwnd / srtt`) is that of
   the first hop, megabytes per second on a loopback or a LAN in front of a slow link, and
   compression then began only once samples arrived, which made its onset depend on timing (the
   S5 test: 0.2 s locally, consistent with 2.8 s instead of 0.9 s on a CI runner);
2. at least 512 bytes are ready to send (keystroke echoes go out raw, at once). When compressing,
   the server reads up to 64 KiB of backlog per message instead of 16 KiB (a larger frame
   compresses better and still respects `MAX_TERMINAL`);
3. the stream looks compressible: an exponentially weighted ratio `ρ` (compressed / raw of each
   chunk compressed, each sample capped at 1.5, α = 0.25, starting at 0.5) of the recent frames
   is below 0.85; when it is above, the server stops compressing and samples one chunk again
   after 1 MiB or 2 s;
4. the frame is at least 10 % smaller than the raw data, else OUTPUT is sent.

Applies to OUTPUT of tty and pipe sessions (compressed `tar` over a pipe session is detected as
incompressible by 3 and sent raw). ERROR_OUTPUT and INPUT are never compressed.

### 7.3 Codec: `ruzstd` encoder, our own bounded decoder

| | `ruzstd` | `zstd` (bindings to libzstd) |
|---|---|---|
| Language | Rust, no C | C library, `zstd-sys` builds the bundled C or links the system's |
| Decoder (client parses server data) | memory-safe, but **unbounded**: it does not limit what one block produces (a sequence can ask for 128 KiB, a block for far more), so a 64 KiB message can expand to gigabytes before any size check, and rule 4 of protocol §7.12 cannot be met with it | memory-unsafe language, very well fuzzed (OSS-Fuzz) |
| Encoder | `CompressionLevel::Fastest` ≈ zstd level 1 (higher levels not implemented yet) | levels 1 – 22 |
| Build | nothing new | a C compiler for every cross target of the static releases (ring already needs one) or pkg-config |
| Distributions | Debian: trixie 0.7.3 (decoder only, no encoder), forky/sid 0.8.3; Fedora: `rust-ruzstd` | Debian: `rust-zstd` 0.13 everywhere; Fedora: `rust-zstd` |
| License | MIT | MIT / BSD-3-Clause (0.14) |
| MSRV | 0.8.3 and 0.9 declare 1.87; 0.8.2 declares none but needs 1.87 (`u32::is_multiple_of`); 0.8.1 builds with 1.85 | 1.64 |

**Decision: `ruzstd` as the encoder only; decoding with our own bounded decoder.** Level 1 is the
right level for interactive streaming anyway (speed over ratio; terminal output compresses
3 – 8× at level 1). No C in the dependency tree and nothing new in the release build are worth
more than higher levels we would not use; DESIGN §3 promises "no bundled C". The receiver's side
is `codec/decode.rs`: RFC 8878 sections 3 and 4 for the frames protocol §7.12 allows (single
segment, no dictionary, at most 64 KiB), about 800 lines of plain Rust over slices, no `unsafe`.
It checks every literal copy and match against the declared content size before making it,
refuses a block larger than the window, allocates at most the declared size plus one block's
literals, and verifies the optional XXH64 content checksum (`twox-hash`). It decodes libzstd
1.5.5 frames of every level and of every block and literal type (test vectors in
`codec/vectors/`), and the fuzz target `zstd_frame` checks that it never panics, that what it
accepts produces exactly the declared size and the same bytes as `ruzstd`'s decoder (run only
on frames ours accepted, which bounds them), and that our own frames of any input round-trip
(security.md §4.6).

The codec is behind two functions in `qsh-core/src/codec.rs` (`compress(&[u8]) -> Option<Vec<u8>>`:
`ruzstd` at its fastest level, the header rewritten to a single-segment frame with the content
size declared; `decompress(frame, max) -> Result<Vec<u8>, DecodeError>`), so switching to libzstd
later is a local change.

**Cargo feature `zstd`** (default on, in `qsh-core` and `qsh-cli`): `ruzstd`, `twox-hash` and
the decoder. A build without it (`cargo build --no-default-features`) never offers the `zstd`
capability, so it neither sends nor accepts compressed data; everything else works, and the
peer simply sends OUTPUT. Versions: `ruzstd = "0.8.1"`, and the lock file keeps 0.8.1, the
newest that builds with our MSRV 1.85 (0.8.2 declares no `rust-version` but needs 1.87, so the
MSRV-aware resolver would pick it; do not `cargo update` it). For packagers: Debian forky/sid
(0.8.3, with a newer rustc) build with the feature; Debian 13 (trixie) has 0.7.3, which has no
encoder, so a trixie build disables the feature.

## 8. `qsh-server doctor`, `qsh-server tune`, `qsh doctor`

This is the per-distribution half of M2: the host side of "optimize itself" needs root, so qsh
cannot do it silently; it finds every problem, says exactly how to fix it on *this*
distribution, and offers to do it after showing a diff.

### 8.1 Report format

Human output, one line per check, a fix line when there is something to do:

```
qsh-server doctor: web1 — Ubuntu 24.04 LTS, systemd 255, kernel 6.8.0, KVM (Amazon EC2)

  ok    daemon         0.4.0 running, UDP+TCP 60443, 3 sessions
  warn  udp-buffers    net.core.rmem_max is 212992; QUIC on long fast paths needs 4194304
                       fix: sudo qsh-server tune --apply
  fail  firewall       ufw is active and allows neither UDP nor TCP 60443
                       fix: sudo ufw allow 60443:60542/udp && sudo ufw allow 60443:60542/tcp
  info  cloud          Amazon EC2: the instance's security group must allow inbound UDP and
                       TCP 60443-60542; this host cannot see it (try `qsh doctor web1` from
                       your client)
  ok    linger         sessions survive logout (KillUserProcesses=no)

1 problem stops a transport, 1 slows qsh down. `sudo qsh-server tune` shows what it would change.
```

Statuses: `ok`; `info` (nothing to do, worth knowing); `warn` (works, but slower or fragile);
`fail` (a transport or a feature cannot work; qsh still works through the remaining transports,
at worst the ssh pipe); `skip` (not applicable or not determinable without root, with the
reason). Exit status: 0 when no check failed, 1 when one did, 2 when doctor itself could not run.

`--json` prints one object, schema version 1, stable check ids:

```json
{"doctor":1,"host":{"name":"web1","os_id":"ubuntu","os_version":"24.04","init":"systemd",
 "kernel":"6.8.0-45-generic","virt":"kvm","container":null,"cloud":"aws"},
 "daemon":{"version":"0.4.0","running":true,"udp":60443,"tcp":60443,"extra_ports":[],
           "cert_sha256":"5f1c…","sessions":3},
 "checks":[{"id":"udp-buffers","status":"warn","summary":"net.core.rmem_max is 212992 …",
            "facts":{"rmem_max":212992,"wmem_max":212992,"wanted":4194304},
            "fix":{"root":true,"tune":"udp-buffers",
                   "commands":["sudo sysctl -w net.core.rmem_max=4194304", "…"]}}]}
```

`cert_sha256` and the ports are included only with `--probe` (8.5), which also starts the
daemon if it does not run. Doctor makes **no network calls** and changes nothing, except
starting the daemon with `--probe`.

Doctor runs as any user. Run as root through sudo, it can also read firewall rules and audit
logs, and it applies the per-user checks (linger, runtime directory, daemon) to `SUDO_USER`.

### 8.4 `qsh-server tune [--apply] [--revert]`

`qsh-server tune` (no flag) is a dry run: it prints, as a unified diff for files and as exact
commands for everything else, what `--apply` would change, and exits. `--apply`:

- requires root (`euid 0`); otherwise it prints the plan and `sudo qsh-server tune --apply`,
  and exits 1. It never calls sudo itself;
- prints the plan again and asks `Apply these changes? [y/N]` on the terminal; without a
  terminal it refuses unless `--yes` is given;
- is idempotent: every fix first checks the current state and is left out of the plan when the
  host already satisfies it; running it twice changes nothing the second time;
- records what it did in `/var/lib/qsh/tune.json` (root, 0600, in a 0700 `/var/lib/qsh`: it
  holds copies of firewall configuration files, `/etc/ufw/user.rules` is 0640): for each change
  the file written with its content, mode and owner before and the SHA-256 of what was
  written, the runtime sysctl values before and after, the firewall rules added with the
  command that removes them, the module loaded, the user whose linger it enabled;
- `--revert` undoes exactly what that record lists and only where the host still matches it:
  a file whose content no longer has the recorded hash is left alone with a warning (the
  administrator changed it); runtime sysctls are set back only where they still have the value
  tune set; files come back with their mode and owner. Afterwards it deletes the record. The
  record is used only when it and `/var/lib/qsh` are root's, not links and not writable by
  group or others, and when every change in it is one tune makes (security.md 4.9): another
  file, program, argument, sysctl or module makes tune refuse the whole record.

What tune may change (and nothing else):

| Fix | Change | Default plan |
|---|---|---|
| `udp-buffers` | `/etc/sysctl.d/90-qsh.conf`: `net.core.rmem_max = 4194304`, `net.core.wmem_max = 4194304` (never lowers a larger value), then applied at once (`sysctl -p /etc/sysctl.d/90-qsh.conf`) | yes |
| `tcp-bbr` | `/etc/modules-load.d/qsh.conf` with `tcp_bbr` and `modprobe tcp_bbr`; in 90-qsh.conf `net.ipv4.tcp_allowed_congestion_control` = the current list plus `bbr`, so the daemon can use BBR on its own TLS sockets without changing the host's default | yes |
| `bbr-default` | in 90-qsh.conf `net.core.default_qdisc = fq` and `net.ipv4.tcp_congestion_control = bbr`: every TCP connection of the host, sshd's included (this is what speeds up the ssh pipe) | only with `--bbr-default` |
| `firewall` | ufw: `ufw allow` rules with comment `qsh`; firewalld: `--permanent --add-service=qsh` (or ports) in the zone of the default route, then `--reload`. Raw nftables / iptables: printed, not applied (8.3) | yes, for ufw and firewalld |
| `low-ports` | in 90-qsh.conf `net.ipv4.ip_unprivileged_port_start = <N>` | only with `--allow-low-ports=N`, with a warning: every local user can then bind every port from N to 1023 (and squat a service's port before it starts); appropriate on a single-user host only |
| `linger` | `loginctl enable-linger <SUDO_USER>` | only when `KillUserProcesses=yes`, or with `--linger` |

tune never runs automatically: not from package scripts, not from the daemon, not from the
client. `qsh doctor HOST --tune` (8.5) runs `ssh -t HOST sudo qsh-server tune --apply` after
saying so, so that the confirmation and the sudo password prompt happen on the user's terminal;
without agent, X11 or port forwarding, and only on a `qsh-server` that root owns in
directories only root can change (by its real path): a `~/.local/bin/qsh-server` is the
user's to replace, so for one there it prints how to install qsh-server for the system
instead (exit 43). As root, doctor and tune run commands with `PATH=/usr/sbin:/usr/bin:/sbin:/bin`.
Inside a container, tune refuses to change sysctls (they belong to the host) and says so.

### 8.5 `qsh doctor [HOST]`

`qsh doctor` without a host checks the client: its UDP buffer limits (with the client
distribution's fix), how it watches the network (netlink / route socket / polling), the current
network's path memory entry (winner, blocked transports, learned keepalive).

`qsh doctor HOST`:

1. Runs `qsh-server doctor --json --probe` over the user's ssh (the discovery command of
   protocol §10.2 with `<SUB>` = `doctor --json --probe`). The JSON comes over ssh, so its
   `cert_sha256` is as trustworthy as a bootstrap reply. A server without `doctor` (before
   0.5.0) gives no pin, so the client cannot probe QUIC and TLS; it reports the ssh pipe's
   result and "qsh-server on HOST is 0.x; upgrade it for a full report".
2. Probes every transport and port from the client the way the race would, at most 6 at a time
   (each is an unauthenticated connection for about 3 s, and the daemon admits 8 per source
   address, protocol.md 6.6: more would be refused by that limit and recorded as the network
   blocking the transport): QUIC and TLS handshake to each announced port (pinned), hello
   exchange, then 3 s with a QUIC keep-alive of 100 ms to collect RTT and loss samples from
   quinn, then GOAWAY. No ATTACH, no session is created. The ssh pipe, meanwhile: time to the
   preface. The report over ssh is read within 60 s and 1 MiB, and every string of it is shown
   as text only (security.md 4.6).
3. Reports per transport and port: works / timeout / refused / reset, handshake time; RTT, loss
   and path MTU; NAT: whether the address in PATH_INFO differs from the client's own source
   address, and whether QUIC and TLS connections got different ports (a port-randomizing NAT);
   the keepalive that will be used.
4. **Diagnoses** by combining both sides, for example: "UDP 60443 times out from here, the
   server's firewall allows it, and the server is on Amazon EC2: the security group most
   likely blocks UDP 60443" or "nothing on the server blocks UDP, and TLS works: your network
   blocks UDP; qsh will use TLS on this network (remembered)".

`qsh doctor HOST --json` prints `{"doctor":1,"client":{…},"server":{…server doctor…},
"probes":[…],"diagnosis":[…]}`.

## 9. Predictive echo (M3) and how M2 prepares for it

Predictive echo stays in M3. M2 provides what it will need and must not get in its way:

- the path memory's `rtt` lets the client decide "slow path, predict" before the first
  measurement on a known network;
- SNAPSHOT is authoritative: on a snapshot the client drops every pending prediction;
- the client's `AltScreen` tracker sees snapshot bytes, so "full-screen program, do not predict"
  stays right after a skip;
- the server's screen model could later answer "is the cursor on an editable line", but M3 must
  not depend on it (it exists only for tty sessions within the caps).

## 10. Daemon upgrade without losing sessions

### 10.1 Mechanism: re-exec in place

Sessions live in the daemon's memory, and their programs are the daemon's children. The daemon
upgrades by **executing the new binary in its own process** (`execve`, keeping its PID), after
writing its state to an inherited file descriptor and clearing close-on-exec on exactly the
descriptors the new image needs: listening sockets, the control socket's listener, every
session's pseudo-terminal master or pipes, the state, the state key and (on Linux) its own old
executable for the fallback.

Why not the alternative the milestone first sketched, handing the descriptors to a separately
started new daemon over the control socket with `SCM_RIGHTS`:

| | re-exec in place | hand over to a new process (`SCM_RIGHTS`) |
|---|---|---|
| Session programs stay children | yes: same PID, `waitpid` keeps working, exit statuses (and pipe sessions' exit codes) are preserved | no: they become children of init or of systemd's user manager; the new daemon can see that they ended (pidfd, pty EOF) but cannot learn their exit status. Linux's `PR_SET_CHILD_SUBREAPER` helps only if the new daemon is a descendant of the old one, and does not exist on macOS |
| Service managers | systemd's main PID and cgroup, OpenRC's pid file: unchanged | the main process exits: systemd treats the unit as stopped and kills its cgroup (`KillMode=mixed`), sessions included, unless notify/MAINPID gymnastics |
| Ports | sockets inherited, never free for another user to take | can be passed too |
| Failure | before the `execve`, everything is checked and the old image continues on any error; after it, the new image falls back to the old one (10.4) | the old daemon keeps running until the new one confirms |

The decisive points are exit statuses and systemd; re-exec in place is how systemd itself
(`daemon-reexec`) and several init systems upgrade without losing their children. The control
socket carries the *request* and the version check (10.3).

### 10.2 When it triggers

- **A newer bootstrap.** `qsh-server bootstrap`, `pipe` and `doctor --probe` send their own
  version with every control request. When the daemon is older (semantic version strictly
  lower; never a downgrade, never the same version) and supports upgrades, it answers
  `{"restarting":true}`, upgrades to the requester's executable, and the requester reconnects
  to the control socket (whose listener survives the exec, so connections queue in its backlog)
  and repeats its request, for up to 10 s. A `qsh host` after a package upgrade thus runs on the
  new daemon, and the user's sessions are still there.
- **Explicitly**: `qsh-server upgrade [--exe PATH]`, which the systemd user unit maps to
  `ExecReload=` (`systemctl --user reload qsh-server`).
- **By itself when idle** (`[server] upgrade = "auto"`, the default): every 10 minutes the
  daemon checks whether the file at the path it was started from now has a different inode, and
  when it does and no session is attached, it probes that file (10.3 step 2) and upgrades if it
  is newer. Security fixes then take effect without waiting for the next login.
  `upgrade = "manual"` turns the automatic paths off; the explicit command still works.
- **Never a failed program again, automatically.** A program (the open file's device, inode
  and change time) refused by the checks or the probe, or an upgrade to which failed in any way,
  is not tried again by the daemon for its lifetime, across upgrades and across the fallback of
  10.4 (the state carries the list, 10.5): requests naming it are served by the running daemon
  as they are, and only `qsh-server upgrade --force` tries it again. A new file at the path is
  a new program. Without this rule a newer `qsh-server` that cannot take over is tried at every
  bootstrap, pipe and doctor, and each attempt ends every connection.
- **An old daemon that cannot upgrade** (0.2.x and every version before the one that ships this
  section): it does not know the request; the new bootstrap just uses it (qsh/1 is the same
  protocol), and `qsh-server status` / doctor say "an older daemon (0.2.0) runs; it is replaced
  when its sessions have ended, or now with `qsh-server stop` (ends them)". The old daemon exits
  by itself an hour after its last session (protocol §12.5) and the next bootstrap starts the
  new one. Keeping the old daemon running is always the fallback.

### 10.3 Sequence

Old image A, new executable P:

1. **Validate P**: an absolute path, resolved (links included) and opened once; from then on
   the open file is P. On it: a regular file; owned by root or by the daemon's user; not
   writable by group or others; executable. Every directory above it owned by root or the user
   and writable by nobody else (its group only when that is the user's private group; never
   by others, `/tmp` included). security.md 4.8.
2. **Probe P**: run `P handoff-probe` as a child (no shell, empty environment except `PATH`,
   5 s timeout, at most 4 KiB of stdout); on Linux the open file itself (`/proc/self/fd/N`),
   elsewhere its path after checking that it still names that file. It prints `{"qsh-server":"0.4.0","handoff":[1]}`:
   its version and the handoff state formats it can read. A must find a common format and P's
   version must be newer (unless `--force`, which still requires a common format). Any failure:
   abort, nothing has changed.
3. **Quiesce**: stop accepting (the listeners stay open, their backlogs hold new connections),
   send GOAWAY with RESTART (protocol §11.2) on every connection and close them (≈ 500 ms to
   flush), stop the pty reader and input writer threads of every session (`sys::Cancel`) and
   wait for them (at most 2 s; a thread that does not stop aborts the upgrade and everything is
   resumed). Output the programs write meanwhile waits in the kernel's pty or pipe buffer; a
   program that fills it blocks for a moment, as when a client is slow.
4. **Serialize** (10.5) into an anonymous file: `memfd_create` on Linux; elsewhere a file
   created in the private runtime directory and unlinked at once. The state is sealed with
   ChaCha20-Poly1305 (ring) under a fresh random 32-byte key, which is written into a pipe
   (32 bytes fit in any pipe's buffer); the new image reads the key from the pipe's read end.
   Session keys therefore never reach a file in clear, even on systems without memfd
   (security.md §4.8).
5. **Clear close-on-exec** on the descriptors of 10.1, and only those, and execute P (on Linux
   the open file, `fexecve`; elsewhere `execve` of its path, checked again first) with
   `["qsh-server", "handoff-resume", "--format=1", "--state-fd=N", "--key-fd=M",
   "--fallback-exe-fd=F"]` and A's environment. This command line is frozen with the state
   format (format 1 means both): every version that reads a format accepts exactly this form,
   recognized before anything else is parsed, so that a later version that renames an option
   or a subcommand still resumes. A's own daemon options (`--on-demand`, `--ports`) travel in
   the state (10.5).
6. If `execve` returns (it failed): restore close-on-exec, restart the threads and listeners,
   tell the requester `{"ok":false,"error":"…"}`, log it. Nothing was lost.

New image B, started with `handoff-resume`:

7. First thing, before parsing its command line or starting its runtime: read the key and arm
   the fallback (10.4). Then decrypt and check the state (format version, lengths, every count
   bounded) and the descriptors: each must be open, of the recorded type (`fstat`: socket,
   character device for a pty master, FIFO for a pipe) and owned by the daemon's user. Until
   the commit the new image works on duplicates of them and leaves the originals untouched.
8. Rebuild the session table (ids, keys, kinds, replay buffers, input queues, exit statuses
   already collected, screen models from their resync snapshots) and create the QUIC endpoints
   on the inherited UDP sockets with the same stateless reset key (10.6). **Commit**: disarm
   the fallback, close the inherited originals (the duplicates stay), restart the threads,
   resume accepting, then `waitpid` every recorded child (programs that ended during the
   upgrade are zombies waiting for exactly this).
9. Log `upgraded 0.3.0 → 0.4.0, 5 sessions kept`.

### 10.4 Fallback after the exec (Linux)

At start every daemon opens its own executable (`/proc/self/exe`, read-only, close-on-exec) and
keeps the descriptor: even when a package upgrade replaces the file, the old inode stays alive
as long as it is open. A passes it as `--fallback-exe-fd`. B arms the fallback before anything
else (10.3 step 7). If B fails anywhere before its commit (10.3 step 8: the state is read-only,
and B has worked on duplicates of the descriptors), its start-up included (reading its
configuration, building its async runtime, its QUIC endpoints), or panics there (a panic hook,
which runs before any unwinding), it executes the old image with `execveat(F, "", …,
AT_EMPTY_PATH)` and the same arguments plus `--fell-back`, and A' (the old version) resumes
from the same state, and remembers P as a failed program (10.2: the state names P). On
macOS there is no `execveat`; the probe in step 2 is the protection there. A crash that is not
a panic (a signal) after the exec loses the sessions, as a crash of the daemon always did; the
fuzzed, bounded state parser and the round-trip tests keep that path small.

### 10.5 State format, version 1

Binary, every integer big-endian, every length bounded and checked before allocation. A string
is a u32 length and UTF-8 bytes; a part in brackets is present only when the flag before it is
1. As built by WP-4 (`server/handoff.rs`):

```
Handoff State {
  Magic (bytes[12]) = "QSH-HANDOFF\n",
  Format (u16) = 1,
  Writer (string, max 64),            // "qsh-server/0.3.0"
  Started (u64),                      // when the daemon first started, Unix ms
  Restarts (u32), Failures (u32),     // upgrades in place so far, and failed ones
  Options (u8),                       // bit 0: on demand; bit 1: a port range follows; others 0
  [First Port (u16), Last Port (u16)],// --ports (or QSH_SERVER_PORTS), 0 < first ≤ last
  Refused Count (u16),                // ≤ 64: programs not to try again by itself (10.2)
  Refused (..) ...,                   // File Id, Failed (u8: 1 an upgrade to it failed)
  Attempt Present (u8), [File Id],    // the program this state was written for

  Port (u16),                         // the primary port (UDP and TCP)
  Listener Count (u16),               // ≤ 32
  Listener (..) ...,                  // kind (u8: 1 UDP, 2 TCP, 3 control, 4 lock file), fd (u32), port (u16)
  Session Count (u32),                // ≤ 100 000
  Session (..) ...,
}

File Id {
  Device (u64), Inode (u64), Change Time (u64: seconds, two's complement), Change Time Nanoseconds (u32, < 10^9),
}

Session {
  Id (bytes[16]), Current Key (bytes[32]), Pending Key Present (u8), [Pending Key (bytes[32])],
  Pid (u32), Generation (u64), Created (u64, Unix ms), Last Seen Age (u64, ms),
  Exit Present (u8), [Kind (u8: 0 exited, 1 signaled), Code (u32), Core Dumped (u8),
                      Signal (string, max 32), Published (u8), [Published Age (u64, ms)]],
  Name Present (u8), [Name (string, max 64)], Command Present (u8), [Command (string, max 1 MiB)],
  Columns (u16), Rows (u16),
  Kind (u8: 0 tty, 1 pipe); tty: Master (u32); pipe: Stdin, Stdout, Stderr (u32 each, 2^32-1 when closed),
  Output Buffer: Capacity (u64, ≤ 1 GiB), Base (u64), Length (u32, ≤ Capacity), Bytes,
  Error Buffer: the same (empty on a tty session),
  Input: Received (u64), Queue Length (u32, ≤ 64 MiB), Queued Bytes, EOF Present (u8), [EOF Offset (u64)],
  Model Present (u8), [Model Columns (u16), Model Rows (u16), Snapshot Length (u32, ≤ 1 MiB = MAX_SNAPSHOT), Bytes],
}
```

Further rules the parser enforces: exactly one control and one lock listener; every descriptor
number at least 3 and named once in the whole state; a session id once; a buffer's bytes within
its capacity and its offsets within 2^64; no trailing bytes; exactly one encoding of every value
(an exit status of kind 0 has no signal and no core flag; kind 1 has code 0), so that decoding
and encoding are inverse, which the fuzz target `handoff_state` checks. An exit whose
`Published` flag is 0 was reaped but not yet announced (its output had not reached its end):
the new image waits for the output and then publishes it, without waiting for the process.
The model's bytes are a resync snapshot (protocol §7.8.4) and are bounded like any snapshot by
`MAX_SNAPSHOT` (1 MiB): a model whose snapshot would be larger, or that cannot be made, is not
handed over (Model Present = 0), and the new image gives the session a fresh model fed from its
output buffer.

Sealed: a random 12-byte nonce, then the ChaCha20-Poly1305 ciphertext and tag of the state,
additional data `"qsh handoff state"`, under a fresh 32-byte key that goes through the pipe.

The lock file's descriptor is inherited too (kind 4): the lock lives as long as the open file,
so no second daemon can start between the `execve` and the new image's first moment.

The stream positions are what make it lossless: output read from the pty before the upgrade is
in the buffer with its offsets, input acknowledged to a client but not yet written to the pty is
in the queue, and both continue at the same offsets after it. A format change that an older
daemon cannot read gets a new `Format` number; the probe (10.3 step 2) negotiates it. The state
parser is a fuzz target.

### 10.6 What clients see

All connections end with GOAWAY (RESTART), a new error code (protocol §11.2): "the server is
restarting in place; sessions are kept". A client reconnects after 500 ms (± 20 % jitter)
without back-off and without ssh, and resumes every session (protocol §7.3): no byte is lost,
and the replay covers what the program wrote during the upgrade. Old clients treat the unknown
code like INTERNAL_ERROR ("reconnect with back-off", protocol §13.2), which also works.

The daemon's QUIC stateless reset key is derived from its identity key (HKDF-SHA256, info
`"qsh stateless reset"`) instead of being random per process, so a client packet for a
connection the new image does not know is answered with a stateless reset the client
recognizes (RFC 9000 §10.3), and the client reconnects at once instead of waiting for its idle
timer. The same helps after a daemon crash.

## 12. Testing: chaos tests and the published benchmark

### 12.1 Unit, property and fuzz tests (every work package)

- **Path memory**: plan construction for every combination of entry state; no poisoning when all
  attempts fail; expiry, bounds, corrupt files; keyed hashes stable across runs.
- **Keepalive learning**: a scripted sequence of PATH_INFO, migrations and idle periods against
  the algorithm of 4.3 (paused tokio time).
- **Snapshot round trip (property test)**: for arbitrary output byte strings and sizes,
  `model₁ ← output`; `data = encode(model₁)`; `model₂ ← arbitrary prefix ++ data` (a terminal in
  some unknown state); then `model₂` equals `model₁` on every item of the content profile. This
  is the definition of correctness of the encoder, and it also checks the handoff's model
  transfer.
- **Snapshot profile check**: `data` contains only the sequences allowed by protocol §7.8.4 (a
  small independent scanner).
- **Fuzz targets** (cargo-fuzz, run in CI like the existing four): `screen_model` (arbitrary
  bytes and resizes into the model and the encoder, round trip), `zstd_frame` (the header check
  and our bounded decoder: exact sizes, never a panic, the same bytes as `ruzstd` where both
  accept, round trip of our own frames), `handoff_state` (the state parser), `path_memory` (the
  file parser).
- **Pacing / catch-up**: the trigger logic as a pure state machine fed with (time, ACK, append,
  input) events; the Ctrl-C budget checked in simulation for RTT 20 – 600 ms; the window
  bounded under a growing queue (`R` is the minimum RTT, 6.3); compression staying on at a
  path rate below the limit although `T` rises above it (7.2).
- **Fault isolation**: a panic injected into a session's model (test hook) disables catch-up
  for that session only; the session, another session's snapshots and the daemon go on.
- **Refused snapshot**: a server that sends a snapshot outside the profile (test hook) gets
  one PROTOCOL_VIOLATION, then an ATTACH of that session without ACCEPT_SNAPSHOT, not a loop.

### 12.2 Chaos harness

A Rust test file `crates/qsh-cli/tests/chaos.rs`, ignored unless `QSH_CHAOS=1` and running as
root, plus the shell helper `tests/chaos/netns.sh` that builds and tears down the topology. In
GitHub Actions (ubuntu-latest has passwordless sudo, `ip`, `tc` with `sch_netem`, `nft`) the
workflow `.github/workflows/chaos.yml` builds once and runs the test binary with `sudo -E`.
Locally: `flock /tmp/heavy.lock sudo -E QSH_CHAOS=1 cargo test -p qsh-cli --test chaos`.

Topology, three network namespaces joined by veth pairs:

```
 qsh-c (client: qsh, ssh, mosh)  ──veth──  qsh-r (router: netem, nft, NAT)  ──veth──  qsh-s (server: sshd, qsh-server, mosh-server)
 10.77.1.2/24, fd77:1::2/64                 10.77.1.1 / 10.77.2.1                    10.77.2.2/24, fd77:2::2/64
```

- netem on both router interfaces (`tc qdisc add dev … root netem delay 135ms 20ms loss 6% rate
  10mbit`), so each direction gets its own delay and loss;
- `nft` in the router to drop UDP (`udp dport 60443 drop`, mid-session), to drop a single port
  (for port fallback), and to masquerade the client's network with a short UDP conntrack timeout
  (`nf_conntrack_udp_timeout = 15`, `_stream = 15`) for NAT rebinding;
- address change: add `10.77.1.3` to the client's veth, replace the default route's source,
  delete the old address (what Wi-Fi → cellular looks like to the kernel and to netlink);
- sshd in the server namespace with a test user and key; qsh-server installed into its
  `~/.local/bin`; the client runs `qsh` on a pseudo-terminal driven by the test (qsh-core's
  `sys` pty helpers), with `QSH_TRANSCRIPT=<file>` set.

`QSH_TRANSCRIPT` (a test hook compiled into every build, documented as unstable) makes the
client append every OUTPUT / OUTPUT_ZSTD (offset, length, SHA-256), OUTPUT_GAP, SNAPSHOT and
reconnect event to a file, so the tests can check the stream exactly without parsing a screen.

## 14. Open questions

- **Q1 (MSRV vs ruzstd), resolved in WP-2.** `ruzstd` 0.8.3 and 0.9 declare Rust 1.87; 0.8.2
  declares no `rust-version` but uses `u32::is_multiple_of` (Rust 1.87), so a `>= 0.8, < 0.9`
  requirement would let the MSRV-aware resolver pick a version that does not build on 1.85
  (Debian 13's rustc). Decision: `ruzstd = "0.8.1"` with the lock file pinned to 0.8.1, the
  newest that builds with 1.85, checked by the MSRV CI job; only its encoder is used (7.3).
  Debian 13's 0.7.3 has no encoder: trixie builds go without the `zstd` feature (no
  compression offered or accepted, everything else works). Revisit when Debian 13 gets a newer
  rustc, or raise the MSRV to 1.87 then.
- **Q2 (vt100 0.15 vs 0.16), resolved in WP-2.** 0.15 lacks the faint attribute and
  `Screen::set_size`, so qsh requires `vt100` 0.16. Debian forky/sid have 0.16.2; Debian 13
  (0.15.2) needs `rust-vt100` 0.16 packaged or vendored (6.2).
- **Q3 (root on test machines).** The chaos tests and `tune --apply` need root. They run in
  GitHub Actions; running them on the user's own servers needs the user's permission (and on the
  development server they must use their own namespaces only; they never touch the host's
  firewall or sysctls).
- **Q4 (publishing).** The benchmark table goes into the public README, and the bench workflow
  installs mosh in CI; publishing numbers that compare with other projects is an outward-facing
  statement the user should approve once (wording and method).
- **Q5 (low ports).** Should tune offer `--allow-low-ports` at all, given its effect on
  multi-user hosts? Recommended: yes, behind the explicit flag and warning, because 443 is what
  makes qsh work in hotels and offices; the M4 system service is the clean answer.

- `Conn::server_restarting() -> bool`: GOAWAY (RESTART) seen. The session then reconnects after

- `Conn::observed() -> Option<SocketAddr>`, `Conn::attempts() -> Vec<(Transport, String)>`,

  condition 3 of 4.2.
- `Conn::ping_due(last_ping) -> bool` (today: 15 s) and `Conn::dead() -> Option<String>`

  are gone.

### Decisions

- **`restarting` only for an upgrade that will happen.** A daemon answers a newer requester
  with `{"restarting":true}` only after the requester's executable passed the checks and the
  probe (10.3 steps 1 and 2). Otherwise it serves the request as it is, and remembers the
  executable (device, inode and change time) so that it does not probe it on every request.
  A replaced file has another inode and is probed again. A program an upgrade to failed is
  remembered the same way (10.2), and a requester still answered `{"restarting":true}` after
  10 s reports an error instead of handing that answer on as its reply.
- **No session changes behind the upgrade's back.** From the moment the daemon quiesces,
  control requests that create or change sessions, open an ssh pipe or stop the daemon are
  answered `{"restarting":true}`; requesters (bootstrap, pipe, status, stop) repeat them for up
  to 10 s. A bootstrap already creating a session finishes first (a lock the upgrade takes).
- **QUIC packets wait for the new image.** After the connections are closed, the QUIC
  endpoints are moved off the daemon's UDP sockets (to two throwaway sockets: quinn keeps
  reading the previous socket until traffic arrives on the new one). What clients send during
  the upgrade waits in the socket's 4 MiB buffer, as TCP connections wait in the listeners'
  backlogs, and the new image answers it.
- **Status.** `sessions` stays the list it was (tests and people read it); the count is
  `session_count`. New members: `udp`, `tcp`, `extra_ports`, `cert_sha256`, `upgrade`
  (`"auto"` / `"manual"`), `can_upgrade` (false for a daemon embedded in another program),
  `handoff` (formats read), `restarts`, `upgrade_failures`, `upgrade_error`, `upgrading`,
  `upgraded_from`.
- **The configuration of the new image** is read again, but the listeners are the inherited
  ones: a changed `extra_ports` takes effect at the next fresh start, never by dropping a port.
- **Embedded daemons** (`ServerConfig::reexec` None: the tests, an embedder) refuse upgrades;
  `qsh-server daemon` sets it with its own options.

### Test hooks (unstable; only in builds with the cargo feature `test-hooks`, which CI's test runs enable and release and distribution builds do not)

- `QSH_TEST_VERSION=X.Y.Z`: the program reports that version (status, probe, requests). An
  upgraded image never inherits it, so a daemon started with an old version upgrades once. The
  chaos `upgrade` scenario can start the old daemon with it instead of building twice.
- `QSH_TEST_UPGRADE_CHECK_MS=N`: `qsh-server daemon` looks for a replaced executable every N
  ms instead of every 10 minutes.
- `QSH_TEST_HANDOFF_FAULT=stop,serialize,exec,start,restore,commit,none`: read by the daemon
  when it starts, one fault per upgrade attempt in order (`start` makes the new image panic
  right after it armed its fallback, `restore` fail its descriptor checks, `commit` fail just
  before its commit; Linux then executes the old image again).
- `QSH_TEST_TRUSTED_DIR=DIR`: the directories above DIR are not checked for the upgrade's
  program (the tests' worlds live in /tmp, which 10.3 step 1 refuses).
- The old image's `QSH_TEST_VERSION` passes to the new one as `QSH_TEST_FALLBACK_VERSION`,
  so that after a fallback the old image reports its old version again.

### For the other packages

- **WP-2**: `OutputSink::handoff()` (default None) returns the model as (columns, rows, resync
  snapshot); it goes into the state, and the new image's session hands it out once through
  `PtySession::take_resumed_model()`.
- **WP-3**: `qsh-server status` has everything the `daemon` check needs (above);
  `can_upgrade` false or a missing `handoff` member means an older daemon (10.2, last item).
- **WP-5**: `crates/qsh-cli/tests/upgrade.rs` runs the upgrade end to end without root
  (explicit, triggered by a newer bootstrap, every failure path); the chaos scenario adds the
  network profiles.

### Known limitations

- A session hung up during the 5 s before an upgrade loses its SIGKILL follow-up (protocol.md
  7.11 step 5): a program of it that ignores SIGHUP keeps running, detached from any session.
- macOS has no `fexecve`: a new image that cannot resume loses the sessions there, as a crash
  would; the probe is the protection (10.4).

### Decisions beyond the text above

- **Attempts outlive their race.** QUIC and TLS attempts that started before the race was
  decided go on for up to 30 s (`Race::conclude_keeping`); one that started no later than the winner
  and is unanswered is marked `timeout` at once, provisionally (section 3.3), so that a blocked transport is seen as a
  timeout 8 s later and recorded (another transport reached the server, so it is not
  poisoning). Without that, a session on a UDP-blocked network would never learn that QUIC is
  blocked: TLS wins after 400 ms, long before QUIC's timeout. A late success is recorded (and
  the connection closed, unless it moves the sessions, below); a failure of a transport that succeeded in the same race, on
  another port, is not; each transport is marked once per race. Attempts that had not started
  are not tried, as before; ssh pipe attempts are abandoned. A late success of a better
  transport than the winner's (QUIC after TLS won, TLS after the pipe won) keeps its
  connection: hello, then a transport upgrade like a probe's (3.6); without a session on the
  winner, or within a minute of the last upgrade, it is closed.
- **Winner ties.** Among transports with a success, one without a `fail` mark (its retry
  passed and it is back in the race) comes before one with, then the most recent `ok`, then
  QUIC, TLS, the pipe. A transport due for a probe is in the race at its configured start.
  When every allowed transport is blocked, the plan is the default one.
- **The ssh pipe** is recorded when it works (it can win the next race at 0 ms), never as
  failed: it is the last resort, and its failures are rarely facts about the network.
- **Hello failures.** No SERVER_HELLO within 5 s is `hello`; a reset or end of the connection
  during the hello is `reset`; an ERROR from the server is not recorded. Over QUIC a missing
  hello is `hello` only if no more than 2 of the server's packets arrived after the handshake:
  a box that blocks the flow lets nothing through, while on a slow path (the terrible profile,
  20 % loss over 600 ms) the server's packets keep coming and the hello is merely late. That
  one used to be recorded, left QUIC out of the next races for a minute, and put the sessions on
  TLS, where a Ctrl-C took 4.6 – 16.8 s (CI, release build).
- **Hellos run concurrently, and a slow one is kept (2026-10-06).** The race used to say hello
  on one connection at a time, in the order the handshakes completed, and to close a connection
  whose hello had no answer after 5 s. On the terrible profile that is a third of the QUIC
  hellos (local rig, 10 of 30 runs: QUIC's handshake done at about 650 ms, its hello exchange
  losing packets twice, and with QUIC's probe timeout of about 1.8 s after the handshake,
  doubled for the second loss, 5 s go by): TLS, connected meanwhile, waited for those 5 s, won,
  and QUIC was thrown away, leaving the session on TLS for good (Ctrl-C 3.0 – 4.9 s there,
  against 0.6 – 2.5 s on QUIC; twice the TLS attach itself got no answer within 5 s and the
  first prompt took 13 – 21 s). Now each connection says hello as soon as it comes out of the
  race; the first SERVER_HELLO wins. A hello without an answer after 5 s is recorded as before
  (`hello` or `error`), but kept until 10 s after it started (`HELLO_PATIENCE`): it may still
  win, or, when a worse transport won meanwhile, answer late and take the sessions over like a
  late handshake (3.6). Hellos of worse transports still under way when the race ends are
  recorded as working and dropped.
- **A slow ATTACH over a path that answers is not abandoned (2026-10-06).** The same losses
  hit the ATTACH: after 5 s without ATTACHED the session abandoned it, closed the connection
  and raced again over the same path (local rig, terrible: 3 of 40 runs, the first prompt or a
  Ctrl-C 5 – 15 s later). Now the 5 s apply only when nothing at all arrived on the connection
  since the ATTACH was sent (over QUIC any datagram counts, the ATTACH's acknowledgement
  among them); while the path answers, the session waits up to 10 s (`ATTACH_PATIENCE`).
- **On a lossy path one handshake timeout blocks nothing (2026-10-06).** On the terrible
  profile about one QUIC or TLS attempt in 10 to 20 runs out of its 8 s by chance, and was
  recorded as a block when another transport won: the next sessions left it out and ran on
  TLS or the ssh pipe (CI: QUIC and TLS both timed out, the pipe won after 23 s, and a Ctrl-C
  over it took 21.5 s; the next run planned the pipe alone). When the entry's measured loss is
  15 % or more (`LOSSY_PATH`), a single `timeout` no longer counts as blocked; the second in a
  row does. Other kinds, and paths below 15 % (S1 at 6 %), are unchanged.
- **Measured with the three changes above** (local rig, debug build, terrible, 40 runs): 40 of
  40 prompts, Ctrl-C p50 1.30 s and p95 2.76 s (before, 30 runs: 1.33 s and 3.76 s, two runs
  over the 3.67 s bound, both on TLS after a QUIC hello took longer than 5 s). One run took
  3.99 s: QUIC's hello got no answer within 10 s at all, and the session stayed on TLS.
- **A session that hung up stays put (2026-10-06).** After `~.` the pump no longer suspects
  its path (3.8) and does not leave its attachment when the pool abandons or retires the
  connection: the EXIT answering the HANGUP comes there, and the server removes the session as
  it sends it, so a move lost the EXIT and the re-attach found SESSION_UNKNOWN (exit 255 instead
  of 129; seen once on macOS CI after a stall). A re-attach after HANGUP that gets
  SESSION_UNKNOWN or SESSION_ENDED ends the session with SIGHUP's status (protocol.md 7.11).
- **A first prompt that never came was ssh's login (2026-10-06).** The chaos runs that showed
  no prompt within 90 s on the terrible profile were, where the client's state was captured,
  still logging in over ssh: the TCP connection to sshd in exponential back-off (sshd's side:
  `rto:99680 backoff:5`, 536 bytes unacknowledged although the client had received them, its
  acknowledgements lost), as `ssh host` itself would be. ssh's logins there take 10 – 50 s
  (`login_s`), with a tail beyond 90 s; the harness now waits up to 300 s for a run that is
  still logging in, and counts such runs (`slow_logins`).
- **Condition 3 of 4.2** is checked with a slack: a PATH_INFO reaches the client up to about
  1 s after the packet that caused the change, and the client may have acknowledged output
  that arrived on the new path in between. The client is "idle" when it sent nothing in the
  2 s before the PATH_INFO and the current silence is at least K, or when the burst of sends
  that started within those 2 s followed a silence of at least K (sends ≥ 1 s apart start a
  new burst).
- **Growth** (4.3) counts attached time only while the network's K is the interval in effect
  (K ≤ the connection's QUIC keep-alive): a connection created with a smaller keep-alive cannot
  test a larger K. "Attached" is "a session holds the connection".
- **Probes.** One probe at a time per connection, of the first due transport; a probe that
  fails for a reason that says nothing about the network (refused) still backs off, keeping
  the recorded kind. A probe is never made on another network than the one the failure was
  recorded on, and its outcome is dropped when the network changed meanwhile.
- **Upgrades** happen only when the old connection carries a session (otherwise there is
  nothing to move, and the server would close the unused probe connection after
  `AUTH_TIMEOUT`); the old connection gets GOAWAY (NO_ERROR) and is closed once its sessions
  left, or after 30 s.
- **`path_memory = false`**: the pool uses a memory that lives only as long as the process
  (learning and probes still work within the process; nothing is read or written). An
  embedder passes `None` to `Pool::with_memory` for the same.
- **Writes**: at most every 10 s from the monitor (in a blocking task), at once after a
  keepalive step, and when the pool is dropped (`Pool` implements `Drop`); RTT and loss are
  measured 5 s after the connection starts, then every 5 minutes and when it ends.

`hello`, `refused`, `pin`, `error`), `plan` (`attempts` with `transport`, `port`, `delay_ms`;

**S1, measured.** `udp-blocked-memory` was report-only while path memory did not learn from a
mid-session block; since the reconnect race marks the unanswered QUIC attempt (above) and, now,
the background race of 3.8 does the same, the plan is `tls@0ms` and both checks are hard. The
attach takes TLS's own exchanges: TCP and TLS handshakes, the hello, the attach, 4 round trips
(1.08 s at 270 ms) plus about 25 ms to start the process. Local rig, debug build, six runs:
race start at 0 ms; handshake and hello 825 – 871 ms, once 1613 ms; attach 246 – 292 ms, twice
about 600 ms; `attach_s` 1.124 – 1.155 s without a retransmission, 1.468 and 2.249 s with one
(earlier runs: 1.104, 1.115, 1.996, 2.075 s; CI, release: 1.12 s). The excess is TCP's
retransmission timeout at 6 % loss (1 s for a lost SYN, about 0.3 s for a lost segment later),
not the build or the CPU: it is bimodal and lies inside the transport's exchanges, never before
the race starts. S1 is met as stated (the working transport starts at once; nothing else is
waited for).

**S1 as a check on several attaches (2026-10-06).** One attach per run made S1 a single-sample
hard timing check on a 6 % loss path, the statistical problem S3 had (6.4): a local run failed
with `attach_s` = 3.00 s, a lost SYN and a second loss. The scenario now attaches 7 times
(`QSH_CHAOS_ATTACHES`), each from a fresh process with the remembered plan (the previous one is
killed, a lost client), and checks the distribution like S3. About k = 8 packets lie on TLS's
critical path (SYN, SYN-ACK, the client's and the server's TLS flights, the hello and the attach
each way); the losses before they are through are negative binomial (6.4): at 6 %, P(L = 0) =
0.61, P(L ≤ 1) = 0.90, P(L ≤ 2) = 0.98, so r50 = 0 and r95 = 2. A TCP recovery costs at most
the retransmission timeout of a SYN, 1 s (a later segment about 0.3 s). The bounds:

- p50 ≤ 2 s (S1 itself; 1.10 – 1.16 s without a loss);
- p95 ≤ 2 s + r95(6 %, k = 8) × 1 s = 4 s;

each as a one-sided binomial test at α = 0.05: with 7 attaches the check allows 1 over the p95
bound (2 have probability 0.044 at the bound) and 6 over the p50 bound. What S1 rules out stays
far beyond either bound: waiting for the 8 s QUIC timeout, or the 3 s pipe stagger followed by
ssh's own handshakes. That TLS starts at 0 ms (`planned_first`) is checked hard in every run, and
the per-run breakdown (race start, handshake and hello, attach) is recorded.

### Decisions beyond the text above

- **Checks.** `selinux` and `apparmor` are two ids (18 lines), each `skip` where its system is
  not in use, so that the JSON has the same ids on every host. Inside a container the host-wide
  checks (`udp-buffers`, `tcp-bbr`, `conntrack`) are `info` at worst and their fixes are for the
  host, not for tune.
- **Firewall verdicts.** ufw needs root to read its rules: without root it is `skip` and the fix
  is the opening command itself, with "if they are not open yet (sudo qsh-server doctor tells)".
  firewalld's zone is read as any user (`--list-all`); the `qsh` service counts with the ports
  of its service file. Raw rulesets are read as root only, nftables from `nft -j list ruleset`
  and legacy iptables from `iptables -S` / `ip6tables -S` (the nf_tables backend's rules are in
  the nft ruleset already). The model evaluates a new UDP or TCP packet to the port, from an
  unknown address, on the default route's interface: every base chain of the input hook must
  accept it; matches it does not understand (source addresses, xt matches, maps other than
  `ct state`) neither accept nor drop, so it errs towards "blocked" only where an explicit drop
  or a drop policy is reached. When ufw or firewalld is active, the raw ruleset (theirs) is not
  judged again.
- **`--ports FIRST-LAST`** on doctor and tune replaces the configured range (single-user hosts
  open just the port in use). **`--root DIR`** (hidden, tests only) makes doctor read, and tune
  read and change, `/etc`, `/proc/sys`, `/sys`, `/var` under DIR, without following any
  symbolic link; no command of the host runs with it, only the stub programs of `--commands
  DIR`, and tune needs no root with it. The tests and the `doctor` CI job use it.
- **tune.** Steps: the modules-load.d file and `modprobe tcp_bbr` (only when bbr is not
  available yet), `90-qsh.conf` (merged into an existing file: keys replaced or appended, other
  lines kept), the runtime sysctls (written to `/proc/sys`, which is what `sysctl -w` does),
  ufw rules (`ufw allow … comment qsh`) or firewalld (`--permanent --zone=Z --add-service=qsh`
  or `--add-port`, then `--reload`), `loginctl enable-linger SUDO_USER`. Linger is only for the
  user who ran sudo; without `SUDO_USER` it is a note. The firewall commands' configuration files
  (`/etc/ufw/user.rules`, `user6.rules`, `/etc/firewalld/zones/Z.xml` and `.xml.old`) are
  recorded before and after: a revert restores them byte for byte and reloads the tool when
  nobody changed them since, else it runs the tool's own delete commands and says so. A second
  apply merges into the record, keeping the earliest "before". Directories tune created (for its
  files and its record) are removed by the revert when empty. `tcp_bbr` is unloaded by the
  revert only when BBR is not the host's default and the module is unused.
- **Record format** (`/var/lib/qsh/tune.json`, mode 0644): `{"qsh_tune":1,"version",
  "created_dirs":[…],"changes":[…]}`, each change `{"kind":"file","path","before","sha256",
  "fixes","created_dirs"}`, `{"kind":"sysctl","fix","key","before","after"}`,
  `{"kind":"module","fix","name"}` or `{"kind":"commands","fix","run","undo","files":[{"path",
  "before","sha256"}],"reload"}`. Another version is refused, never guessed at.
- **`--probe`** that cannot start the daemon is a `fail` of `daemon` naming the control socket
  and the daemon's log.
- **Discovery** is checked as `env -i sh -c 'command -v qsh-server'` (a login-less shell's
  default `PATH`) and `~/.local/bin/qsh-server`: an approximation of sshd's `PATH`, which the
  shell's startup files may extend.
- **`qsh doctor HOST`** finds the report as the last JSON line with `"doctor"` (login banners
  may come first); exit 42 or 127 is "no qsh-server", exit 2 with "unrecognized subcommand" an
  older qsh-server. Probe outcomes are recorded in path memory as a race would record them (a
  failure only when another transport worked; the ssh pipe never as failed). NAT: the address
  the server reports (PATH_INFO) against the source address the kernel picks towards the server.
  TLS's RTT is the hello exchange. Exit status: 1 when a check failed, no direct transport
  works or there is no report, 2 when neither the report nor any probe worked.
- **JSON** members come out in sorted order (serde_json without `preserve_order`); the man

### Decisions beyond the text above

- **`vt100` 0.16, not 0.15** (Q2): 0.15 has neither the faint attribute nor `Screen::set_size`.
  What `vt100` lacks and how: blink, invisible and strikethrough are not kept (not reproduced);
  DECSTR is emulated with sequences it knows; focus, 1015, the cursor style and titles come from
  the scanner; its scroll regions are private (the model follows them itself, per screen as
  `vt100` keeps them); the normal screen while the alternate one is active is read from a copy
  that leaves it with `CSI ? 1049 l`.
- **`vt100` and `vte` bugs avoided**: a terminal of one column or one row makes `vt100` panic on
  a wrap (models from 2 × 2); a resize that narrows can leave a wide character in the last
  column, and writing over it panics (the model is rebuilt at the new size from its snapshot);
  `vte` 0.15.0 drops the character after a multi-byte character split across two calls (the
  model holds such a start back; a snapshot is then taken just before it, its `Offset` a few
  bytes below the end). The fuzz target `screen_model` runs with debug assertions for the rest.
- **Lazy feeding** (the 100 MB/s budget): `vt100` scrolls at about 10 MB/s on `yes`. Simple
  output (text, line feeds, SGR, OSC) on the normal screen without a scroll region is kept, and
  only what is still visible is ever fed: beyond 2 × rows + 100 line feeds after a CR LF,
  everything before is dropped but its SGR sequences. Exact (a property test compares it with
  direct feeding). Measured on a 200 × 50 model, optimized build: `seq` 306 MB/s, a colored
  build log 115 – 153 MB/s, `yes` 266 MB/s, `cat` of the source tree 207 – 231 MB/s, a
  full-screen redraw stream like `top` 58 MB/s (`vt100`'s own speed); capture and encode of a
  200 × 50 skip snapshot with its tail: 1.4 ms, 13.8 KB.
- **Our own zstd decoder.** `ruzstd`'s decoder does not bound what one compressed block produces:
  a sequence can ask for 128 KiB, so a single 64 KiB message could expand to gigabytes before any
  check, and rule 4 of protocol 7.12 cannot be met with it. `codec/decode.rs` (RFC 8878 sections
  3 and 4, about 800 lines, no unsafe) checks every copy against the declared size before making
  it; it decodes libzstd 1.5.5 frames of every level, block and literal type (vectors in
  `codec/vectors/`) and is fuzzed differentially against `ruzstd`. `ruzstd` stays the encoder.
- **`ruzstd` versions** (Q1): 0.8.2 declares no `rust-version` but uses `u32::is_multiple_of`
  (Rust 1.87); the lock file keeps 0.8.1, which builds with 1.85. Debian 13's 0.7.3 has no
  encoder: a build there goes without the `zstd` feature (no capability offered). `twox-hash`
  (XXH64) verifies the optional content checksum.
- **R is the smallest recent RTT, not the smoothed one**: with `srtt` the window builds a queue,
  the queue raises `srtt`, which raises the window (`1.25 × T × (R + 100 ms)` grows without
  bound). A decaying minimum (30 s) of QUIC's estimate, or of PING over the mux layer (every 5 s
  while attached, and at each attach).
- **Compression decides on the path's rate**: `T` counts offsets, so compression raises it; the
  policy compares `T × ratio` (while compressing) with 4 MiB/s, else compression would turn
  itself off at once on a slow path and back on 10 s later.
- **Triggers**: the input trigger ignores the hysteresis (a Ctrl-C right after a backlog
  snapshot would otherwise wait up to a second, against S3) and a snapshot in flight (it would
  wait for its acknowledgement); output that fell out of the replay buffer is skipped
  (OUTPUT_GAP) whatever is in flight, right before the output after it; a gap on an attachment that takes
  snapshots is followed by a resync snapshot, and so is an attach at LATEST, instead of a
  SIGWINCH. A snapshot that cannot be made (over `MAX_SNAPSHOT`, no model) falls back to
  OUTPUT_GAP and a redraw, with the hysteresis of a snapshot; a resync snapshot to the redraw
  alone; the backlog trigger then waits for more output. A session whose model is gone at an
  attach is attached as one without snapshots (replay, gap and redraw as in 0.2.0), since no
  resync snapshot could follow the cut. At most one snapshot is in flight per attachment, and
  one more sent for input.
- **Hardening after the network-facing review** (before 0.5.0): the scanner became a filter in
  front of `vt100` (strings never reach it, counts clamped, sequences held back until complete)
  and each model has a work budget (6.2, "Hostile output"); the model is fed outside the output
  buffer's lock and reached from the attachments on blocking threads; RESIZEs are coalesced per
  turn of the attachment; the delivery rate has a minimum sample time and a growth cap (6.3);
  output in flight and `U` count skipped ranges exactly (protocol §7.6); the daemon and the
  client answer at most 16 PINGs ahead of the writer; the final ACK after DETACH is written
  within 2 s or not at all; the client checks the offsets of OUTPUT_GAP, SNAPSHOT and
  decompressed output against what it can count (protocol §7.3).
- **Encoding beyond the letter of 7.8.4** (all now written into protocol §7.8.4 after the
  review below): the scroll-push only when the normal screen is
  active; the tail is the lines that scrolled since the client's offset, at least (line feeds
  counted per chunk, minus rows − 1, at most 100); a row written to its last column that does
  not wrap is erased first (EL), so that a wrap flag the terminal kept from before goes; a row
  the previous one wraps into gets at least one character; a scroll region of one row (left by a
  resize) cannot be set and is left out.
- **Client**: every snapshot is checked against the profile before any of it is written (7.8.4
  allows it), and refused with PROTOCOL_VIOLATION; the line before a skip snapshot of the normal
  screen (`qsh: skipped 3.2 MB of output`, dim) is written by the session itself, in order with
  the output, so embedders get it too.
- **Test hook** (`test-hooks` feature): `QSH_TEST_THROTTLE=<bytes per second>` makes each
  attachment send at most that much (wire bytes), a slow link without root.

### Measured in the tests

- S3 in simulation (`pacing/tests.rs`, link 250 kB/s – 10 MB/s, 16 KiB snapshot): within
  2 RTT + 100 ms + S/T for RTT ≥ 100 ms (270 ms: 461 – 490 ms against 642 – 706 ms; 600 ms:
  0.84 – 1.10 s against 1.30 – 1.37 s), within the p95 bound below 100 ms, where the 100 ms of
  slack in the window dominate.
- Ctrl-C during `yes` at 300 kB/s (RTT ≈ 0): 132 – 241 ms at the protocol level
  (`qsh-core/tests/catchup.rs`), 55 ms on the terminal end to end (`qsh-cli/tests/catchup.rs`,
  polled every 50 ms); the backlog was megabytes.
- S5: a 1.5 MB build log at 300 kB/s in 0.43 s instead of 4.97 s (frames 0.088 of the bytes),
  0.90 s instead of 5.09 s end to end with the connection; byte for byte the same.
- S3 on the chaos profiles (`flood-interrupt`, debug build, local rig, all runs pooled; S3
  bounds in brackets), before and after the interrupt fixes of 6.3 and 6.4 (the input trigger
  not waiting for a snapshot in flight, no gap per chunk while the window is full, ACKs at most
  one per 10 ms, tail probes):

  | Profile | Before: runs, p50, p95, max | After: runs, p50, p95, max |
  |---|---|---|
  | crossborder (653 / 1123 ms) | 20, 706, 1004, 1025 ms | 40, 390, 903, 983 ms |
  | lossy (716 / 1216 ms) | 12, 1016, 1650, 1751 ms | 24, 452, 1020, 1392 ms |
  | terrible (1366 / 2166 ms) | 8, 18.0 s, 28.5 s, 28.7 s | 16, 1317, 2421, 2700 ms |

  The runs without a lost packet take 270 – 360 ms on crossborder and lossy; the others pay one
  QUIC recovery each (6.4, "Ctrl-C budget with loss"). Before, a Ctrl-C that arrived while a
  backlog snapshot was in flight waited for that snapshot's acknowledgement (most crossborder
  runs), and the gaps sent per chunk overflowed netem's queues on the lossy profiles (CI, release
  build: terrible p95 68 s).

### Interfaces for the others

- `screen::Live`, `screen::Model`, `screen::snapshot::{encode, check_profile, equivalent}`,
  `codec::{compress, decompress}` are public (the fuzz targets use them).
- `PtySession::window_size()` (pty.rs, three lines) gives a new model its size.
- `OutputSink::handoff` is implemented: an upgrade hands the model over as a resync snapshot.

### Specification review after WP-2

The documents now say what WP-2 built where the build was right, and say what the code must
still change where the documents were right:

- Written into the specification: `R` is the decaying minimum RTT (protocol §7.6, 6.3);
  compression compares the path's rate `T × ρ` with `COMPRESS_BELOW` (protocol §7.12, 7.2);
  the hysteresis applies to the backlog trigger only (protocol §7.8.5, 6.4); EL only with the
  default pen, defined exactly as `check_profile` tracks it, and the stricter parameter rules it
  enforces (protocol §7.8.4); no scroll-push while the alternate screen is active, the tail
  approximate and never relied upon (protocol §7.8.4, 6.6); blink, invisible and strikethrough
  in the profile, left out by models without them (protocol §7.8.4); our own decoder and the
  `zstd` feature (7.3, Q1, security.md §4.6); `vt100` 0.16 (6.2, Q2).
- Still to implement:
  1. **Refused snapshot** (protocol §7.8.4, "After a refused snapshot"; 6.7): the client
     re-attaches that session without ACCEPT_SNAPSHOT for the rest of the process, logs a
     warning (session, offset, reason) and counts it in `Status`/`~s`; after a rejected zstd
     frame (at the latest the second) it stops offering `zstd` to that server for the rest of
     the process. The server logs
     a PROTOCOL_VIOLATION or FRAME_ERROR that follows a snapshot or compressed output.
  2. **Fault isolation** (protocol §7.8.7, 6.2): release builds unwind; `catch_unwind` around
     every call into the model, the encoder and the codec; a panic drops the session's model
     (catch-up off for that session, logged once) or sends the message uncompressed; on the
     client a panic while decompressing fails the channel or the connection, with the fallback
     of item 1. (In progress at the time of this review.)
  3. **Handoff snapshot bound** (10.5): `server/handoff.rs` bounds Snapshot Length by its own
     `MAX_SNAPSHOT` of 16 MiB; it must use the protocol's 1 MiB
     (`proto::message::MAX_SNAPSHOT`), which is all a writer can produce.
